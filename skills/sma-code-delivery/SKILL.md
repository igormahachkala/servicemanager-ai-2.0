---
name: sma-code-delivery
description: "Порядок ведения задачи в этом репозитории: от какой ветки создавать, как именовать, что делать с коммитами, как откатывать слияние и возвращать откаченную ветку. Обязательно применять, когда пользователь начинает любую задачу с изменением кода, спрашивает, от какой ветки ветвиться, как назвать ветку, куда сливать, как откатить изменение или вернуть откаченное. Применять при словах: начинаю задачу, создать ветку, ревёрт, откатить релиз, вернуть ветку, порядок доставки, куда мержить. Порядок, заданный скилом, имеет приоритет над разделами Git Flow в docs/04_DEVELOPMENT_WORKFLOW.md и Release Path в docs/12_RELEASE_PROCESS.md: там описан порядок до введения ствола. Развёртывание в скилл не входит, для него sma-deploy-stage."
---

<purpose>
Ветвление и работа над задачей. Заканчивается коммитами в ветке задачи.
Развёртывание не входит: после завершения работы применить sma-deploy-stage (skills/sma-deploy-stage/SKILL.md).
</purpose>

<precedence>
Порядок ветвления и доставки кода определяют skill, не документация.
Разделы Git Flow в docs/04_DEVELOPMENT_WORKFLOW.md и Release Path
в docs/12_RELEASE_PROCESS.md описывают порядок до введения ствола:
веток prod и beta там нет, доставка кода мимо origin допускалась.
При расхождении верны skill. Документация остаётся источником наборов
проверок и описания устройства проекта.
</precedence>

<invariants>
<i>prod — код, развёрнутый в Production.</i>
<i>beta — код, развёрнутый на Stage.</i>
<i>beta никогда не вливается в prod. Каждая задача попадает в prod своим PR.</i>
<i>beta должна содержать prod. Соблюдение проверяется в deploy-stage и deploy-prod.</i>
<i>Доказательством является вывод команды. Память и документация доказательством не являются.</i>
</invariants>

<protocol>
<p>Выполнять шаги по порядку, не пропуская.</p>
<p>Если expect не совпал с фактом — выполнить on_failure, не интерпретировать.</p>
<p>Решения из ask_user самостоятельно не принимать.</p>
</protocol>

<step id="0" name="проверить готовность машины">
<why>
Настройка машины разовая, но подтверждать её надо до начала работы.
Иначе агент на ненастроенной машине напишет код, дойдёт до развёртывания
и упрётся: ключ не добавлен, нужен человек с root. Работа не потеряется —
она в ветке, — но человека придётся ждать на час позже, чем можно было.
</why>
<command>
ssh -o BatchMode=yes sma 'whoami'
gh auth status
</command>
<expect>whoami возвращает deploy. gh: Logged in to github.com.</expect>
<on_failure>
Не выполнять настройку самостоятельно и не начинать работу.
Сообщить пользователю, что именно не прошло, и передать порядок настройки:
sma-agent-setup (skills/sma-agent-setup/SKILL.md). Часть шагов требует root и выполняется человеком.
</on_failure>
<note>
Это подтверждение, а не повтор настройки. Полная проверка состояния сервера —
блок verify_server в sma-agent-setup (skills/sma-agent-setup/SKILL.md), она нужна только при подключении
новой машины либо при отказе.
</note>
</step>

<step id="1" name="зафиксировать критерий приёмки">
<action>
До начала работы записать: что должно измениться и как это проверить на Stage.
Формулировка проверяемая — команда с ожидаемым выводом либо конкретное
действие в интерфейсе с ожидаемым результатом.
</action>
<example task="убрать предупреждения compose">
Вывод docker compose config для контура не содержит строк
"variable is not set". Полные команды — в деплойных skill, блок contour.
</example>
<example task="заменить шрифты на локальные">curl -s &lt;css&gt; | grep -c googleapis → 0</example>
<example task="исправить отрисовку завершённых заявок">На /m раскрыть группу локаций, вкладка «Завершённые» — карточки отображаются.</example>
<on_missing>Критерий не сформулирован — спросить пользователя, не начинать работу.</on_missing>
<carry>Критерий переносится в тело PR и в сообщение тега stage-ok.</carry>
</step>

<step id="2" name="создать ветку задачи">
<command>
git fetch origin
git switch -c &lt;тип&gt;/&lt;тема&gt; origin/prod
</command>
<naming>fix/ | feat/ | docs/ | chore/</naming>
<expect>git rev-parse HEAD равен git rev-parse origin/prod</expect>
<on_failure>
Ветка создана не от prod. Пересоздать поверх, не удаляя:
git switch -C &lt;тип&gt;/&lt;тема&gt; origin/prod
Флаг -C переставляет существующую ветку на указанное основание.
Удаление тут не нужно и пересекалось бы с запретом ниже.
</on_failure>
<constraint>Не от beta, не от другой ветки задачи, не от локального HEAD.</constraint>
</step>

<step id="3" name="работа и коммиты">
<constraint>Одна задача — одна ветка. Коммитов в ветке может быть несколько.</constraint>
<constraint>После слияния ветки в prod она закрыта. Доработка ведётся в новой ветке.</constraint>
<exception name="откат слияния">
Единственное исключение: слияние ветки в prod было отменено revert-ом.
Тогда ветка снова открыта, исправление ведётся в ней. Порядок возврата
описан в sma-deploy-prod (skills/sma-deploy-prod/SKILL.md), блок rollback.
Причина: повторное слияние ветки после отката ничего не приносит,
её коммиты остаются предками prod. Содержимое возвращает revert от revert
в prod, после чего новые коммиты ветки сливаются обычным порядком.
</exception>
<constraint>Формат: тип(скоуп): суть. Тело объясняет причину, не пересказывает diff.</constraint>
<command>
git add &lt;конкретные файлы&gt;
git status --short
git diff --check
</command>
<expect>git status --short содержит только файлы задачи. git diff --check пуст.</expect>
<on_failure>Присутствуют посторонние файлы. Остановиться, выяснить происхождение, не коммитить.</on_failure>
</step>

<step id="4" name="завершение">
<action>Работа над задачей закончена. Перейти к sma-deploy-stage (skills/sma-deploy-stage/SKILL.md).</action>
<constraint>Тесты, PR и развёртывание в этот skill не входят.</constraint>
<if_skill_missing>
Скилл развёртывания недоступен — файла нет либо он не читается. Остановиться
и сообщить пользователю. Разворачивать самостоятельно запрещено: ни на Stage,
ни в Production, ни по памяти, ни по старым файлам в skills/ вне каталогов
скилов. Порядок доставки задан только скилами.
</if_skill_missing>
</step>

<forbidden>
<group name="запись в стволовые ветки">
<f>Прямой commit и push в prod. Без исключений, только через PR.</f>
<f>Прямой commit и push в beta с кодом задачи. Только через PR.</f>
<f>Коммитить в каталогах развёртывания на сервере.</f>
</group>
<group name="ветки задач">
<f>Создавать ветку задачи не от origin/prod.</f>
<f>Дорабатывать задачу в ветке, уже влитой в prod. Исключение — ветка, слияние которой отменено revert-ом.</f>
<f>Удалять ветку задачи до слияния в prod.</f>
<f>Удалять ветку, помеченную тегом keep, после слияния в prod. См. branch_keep ниже.</f>
<f>Сливать повторно ветку, слияние которой было отменено, без revert от revert в prod. Отказа не будет: git ответит Already up to date либо принесёт только новые коммиты, а отменённое содержимое не вернётся.</f>
</group>
<group name="маршрут">
<f>Придумывать ускоренный маршрут или обход Stage при аварии. Его нет намеренно, см. блок emergency в sma-deploy-prod (skills/sma-deploy-prod/SKILL.md).</f>
</group>
</forbidden>

<branch_status>
<b name="prod">
Строгая. Изменения попадают только слиянием PR. Force push запрещён.
Ветка соответствует коду, работающему у пользователей.
</b>
<b name="beta">
Расходная. Код задач попадает только слиянием PR, но две служебные операции
выполняются напрямую:
  1. слияние prod в beta — восстановление инварианта beta ⊇ prod после релиза;
  2. сброс beta = prod — очистка контура, git push --force-with-lease.
Других причин писать в beta напрямую нет.
</b>
<rationale>
Сброс beta технически невозможен через PR: force push так не делается.
Защищать beta наравне с prod означает отказаться от очистки контура,
и beta накопит отброшенные задачи. Поэтому граница beta проведена правилом
в этом документе, а не настройкой GitHub.
</rationale>
</branch_status>

<branch_keep>
<what>
Тег keep/&lt;ветка&gt; в origin запрещает удаление ветки при закрытии задачи.
Введён 1 сентября 2026. Первый носитель — keep/docs/skills-flow-002:
к этой ветке обращаются агенты Игоря напрямую.
</what>
<why>
По умолчанию ветка после слияния в prod закрыта и удаляется. Часть веток
нужна и после: на них ссылаются внешние агенты, документация, разбор
истории. Признак надобности нельзя держать в памяти агента — ветку удалит
другой агент, который об этом не знает. Тег виден всем после git fetch.
</why>
<set>
Ставит тот, кому ветка нужна после слияния, до закрытия задачи:

git tag -a keep/&lt;ветка&gt; origin/&lt;ветка&gt; -m "Ветка сохраняется
причина: &lt;зачем нужна&gt;
кто обращается: &lt;агент, документ, задача&gt;
дата: &lt;дата&gt;"
git push origin keep/&lt;ветка&gt;
</set>
<check>
Проверка перед удалением — шаг 12 sma-deploy-prod
(skills/sma-deploy-prod/SKILL.md), блок keep_branch. Проверять по origin:
git ls-remote --tags origin 'refs/tags/keep/&lt;ветка&gt;'
</check>
<scope>
Тег держит только ветку. На тег stage-ok, на слияние и на порядок доставки
он не влияет: задача закрыта, доработка ведётся в новой ветке обычным
порядком.
</scope>
<remove>
Снимается, когда надобность отпала, по решению того, кто ставил.
Удаление тега — вопрос пользователю, как и удаление ветки.
</remove>
</branch_keep>
