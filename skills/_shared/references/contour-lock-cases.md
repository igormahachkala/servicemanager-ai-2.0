<contour_lock_cases>

<classify>
Наткнувшись на чужой замок, собрать факты и показать их пользователю
одним сообщением. Снятие в любом случае за пользователем, агент не решает.

Что собрать:
  тело замка                      git tag -l --format='%(contents)' &lt;stage-busy | prod-busy&gt;
  возраст                         git for-each-ref --format='%(creatordate:iso)' refs/tags/&lt;stage-busy | prod-busy&gt;
  ветка существует в origin       git ls-remote --heads origin '&lt;ветка из поля branch&gt;'
  состояние PR                    gh pr list --head &lt;ветка&gt; --state all --json number,state
  что развёрнуто на контуре       ssh sma 'cd &lt;workdir контура&gt; &amp;&amp; git rev-parse HEAD'
  входит ли ветка замка           git merge-base --is-ancestor origin/&lt;ветка&gt; &lt;вершина контура&gt;

<threshold contour="stage">4 часа</threshold>
<threshold contour="production">2 часа</threshold>
<why_threshold>
Порог не снимает замок и ничего не запрещает. Он меняет только формулировку
доклада: агент говорит «похоже на брошенный» вместо «контур занят».
Production занимают ненадолго, порог там ниже.
</why_threshold>

<case name="ветки нет в origin">
Замок мусорный: задача закрыта, ветка удалена, снимать замок было некому.
Ложных срабатываний здесь не бывает. Сказать прямо и предложить снять.
</case>
<case name="ветка есть, PR слит, возраст больше порога">
Похоже на брошенный: слияние прошло, а до снятия замка агент не дошёл.
Показать факты, назвать владельца из поля agent, предложить два пути —
найти владельца либо снять замок.
</case>
<case name="ветка есть, PR открыт">
Агент остановился между постановкой замка и слиянием. Контур при этом чист:
его код в beta не попал, снятие замка последствий не имеет. Самый безобидный
случай, но решение всё равно за пользователем.
</case>
<case name="возраст меньше порога">
Контур занят, идёт работа. Ждать. Ничего не предлагать.
</case>

<contour_state>
В докладе показывать и состояние контура: входит ли ветка замка в развёрнутую
вершину. Входит — код брошенной задачи лежит на контуре, и снятие замка его
оттуда не убирает: следующее развёртывание пойдёт поверх. Тогда решается
не только судьба замка, но и нужен ли сброс beta.
</contour_state>
</classify>

<foreign_lock>
Чужой замок агент не снимает по своему решению. Ни при каких обстоятельствах,
включая полную уверенность, что владелец о нём забыл.
Порядок: собрать факты блоком classify, показать пользователю, ждать команды.
Снятие выполняется только по явной команде и сопровождается блоком lock_void.
<why>
Снятие пускает следующего агента на контур, который может быть занят
по-настоящему. Признак «брошенный» — вероятностный, а последствия ошибки
приходятся на живого владельца.
</why>
</foreign_lock>

<lock_void>
<when>Пользователь распорядился снять чужой замок.</when>
<command>
git tag -a lock-void/&lt;ветка из поля branch&gt; -m "Чужой замок снят
lock: &lt;stage-busy | prod-busy&gt;
owner: &lt;поле agent из тела снятого замка&gt;
age: &lt;возраст на момент снятия&gt;
reason: &lt;почему сочли брошенным&gt;
by: &lt;кто снял&gt;
date: &lt;дата и время UTC&gt;"
git push origin lock-void/&lt;ветка из поля branch&gt;

git push origin :refs/tags/&lt;stage-busy | prod-busy&gt;
</command>
<why_branch_in_name>
Имя lock-void содержит ветку, в отличие от самого замка. Столкновение имён
здесь не нужно и вредно: запись адресована конкретному владельцу, и он ищет
её по имени своей ветки. Двум снятым замкам разных веток нужны две записи.
</why_branch_in_name>
<order>
Сначала поставить lock-void, потом снять замок. Обратный порядок оставляет
промежуток, в котором контур свободен, а объяснения не существует.
</order>
<why>
Владелец, если он жив, вернётся и не найдёт своего замка. Без записи он
не отличит собственную ошибку от чужого вмешательства и может продолжить
работу на контуре, который уже занят третьим агентом.
</why>
<cleanup>
Тег lock-void снимает тот, кто его ставил, после того как владелец
объявился либо стало ясно, что не объявится. Удаление тега — вопрос
пользователю.
</cleanup>
</lock_void>

<own_lock_missing>
<when>
Агент дошёл до снятия своего замка, а замка в origin нет — либо замок есть,
но поле branch его тела называет чужую ветку. Второе означает то же самое:
своего замка нет, а контур успел занять другой агент.
</when>
<action>
Остановиться. Не считать это мелочью и не продолжать работу на контуре.
Чужой замок, оказавшийся на месте своего, не снимать.
Проверить, не снимал ли замок кто-то другой:

git ls-remote --tags origin 'refs/tags/lock-void/&lt;ветка&gt;'
git fetch origin tag lock-void/&lt;ветка&gt;
git tag -l --format='%(contents)' lock-void/&lt;ветка&gt;

Тег есть — замок сняли, причина в теле. Контур мог быть занят другим
агентом после снятия: проверить занятость блоком check и показать
пользователю обе записи.
Тега нет — замок исчез необъяснимо. Сообщить пользователю, дальше
не работать с контуром.
</action>
</own_lock_missing>

<not_covered>
<item>
Автоматического снятия брошенных замков нет и не планируется. Признак
вероятностный, решение остаётся за пользователем — блоки classify
и foreign_lock. Следствие: пока пользователь не ответил, контур занят.
</item>
<where>Реестр: _claude/tasks/git-flow/open-questions.md.</where>
</not_covered>

<stale_local_tags>
Локальные теги замков надо вычищать: git fetch --prune --prune-tags origin.
Обычный fetch снятые в origin теги не удаляет, они копятся в каждой копии.
Мест, где это обязательно, два: перед постановкой замка, блок acquire,
и в каталоге развёртывания, шаг 8 обоих скилов.

Отдельный случай — переход с прежней схемы имён stage-busy/&lt;ветка&gt;
на фиксированное имя. Пока старый тег жив, тег с именем stage-busy создать
нельзя: имя ссылки не может быть префиксом имени другой ссылки.

Текст отказа зависит от того, как хранятся ссылки, а не от сути:

  распакованные:  cannot lock ref 'refs/tags/stage-busy':
                  'refs/tags/stage-busy/&lt;ветка&gt;' exists;
                  cannot create 'refs/tags/stage-busy'
  упакованные:    'refs/tags/stage-busy/&lt;ветка&gt;' exists;
                  cannot create 'refs/tags/stage-busy'

Отказ валит весь fetch, а не одну ссылку: не обновляются ни ветки, ни теги.
Лечится удалением старого тега — git tag -d stage-busy/&lt;ветка&gt; — либо
тем же --prune-tags, если в origin его уже нет.
<why_not_directory>
Распакованная ссылка со слешем в имени — это файл в подкаталоге
.git/refs/tags/stage-busy/, и кажется, что мешает именно каталог. Каталог
здесь следствие способа хранения, а не причина. После git pack-refs --all
распакованных файлов не остаётся вовсе, ссылка лежит строкой в packed-refs,
каталога на диске нет — создание тега всё равно отклоняется. Проверено
запуском 2 сентября 2026.
Практическое следствие: искать и удалять каталог руками бесполезно, лечит
только удаление ссылки командой git.
</why_not_directory>
<scope>
Каталог, если он есть, лежит внутри .git каталога развёртывания. В рабочее
дерево ничего не попадает, git status его не видит, правило о каталоге
развёртывания он не нарушает. Ломается другое: fetch в этом каталоге,
из-за чего каталог отстаёт от вершины ветки — то, что ловят сверки
шага 10 Stage и шага 9 Production.
</scope>
Проверено 2 сентября 2026 в /opt/sma-beta.
<clobber_not_error>
Второй отказ, внешне похожий на первый и ошибкой не являющийся. В каталоге
развёртывания лежит копия замка, снятая с origin раньше, а в origin под тем же
именем стоит замок другого агента: объекты разные, и fetch печатает

  ! [rejected]  stage-busy -&gt; stage-busy  (would clobber existing tag)

Флаг --prune-tags здесь не срабатывает: он удаляет теги, которых в origin
нет, а этот есть. Обновить существующий тег на другой объект fetch без --force
отказывается намеренно — это защита от подмены тега.

Останавливаться не надо. Отклонена одна ссылка — тег замка; ветки при этом
обновлены, git pull следом проходит, каталог встаёт на вершину ветки. Замки
читает агент на своей машине, каталог развёртывания их не читает вовсе,
и устаревшая копия там ни на что не влияет.

Строка пропадёт сама: как только владелец снимет замок в origin, следующий
fetch удалит копию флагом --prune-tags.

<how_to_tell>
По коду возврата эти два отказа не различаются: fetch завершается кодом 1
в обоих случаях. Проверено запуском 2 сентября 2026 в /opt/sma-prod, повторно
воспроизведено.

Различие видно в выводе fetch и в результате pull:

  would clobber   в выводе отклонён только тег замка, строки обновления
                  веток присутствуют; git pull --ff-only проходит,
                  каталог встаёт на вершину ветки
  D/F-конфликт    ни одной строки обновления, за fetch не проходит pull,
                  каталог остаётся на прежнем коммите

Первое — продолжать. Второе — разбирать по началу этого блока.
</how_to_tell>
<no_chaining>
Команды fetch, checkout и pull в шаге 8 обоих скилов выполняются отдельными
вызовами и через &amp;&amp; не связываются. Код 1 от fetch при отклонённом теге замка
оборвал бы цепочку до pull, и каталог остался бы на прежнем коммите — то есть
безобидная строка превратилась бы в настоящее отставание каталога.
</no_chaining>

ветки feat/mobile-shift-gate-080, в /opt/sma-prod — копия замка ветки
skills/contour-lock-fix.
</clobber_not_error>
</stale_local_tags>
