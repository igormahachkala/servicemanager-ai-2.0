<purpose>
Замок контура. Не даёт двум агентам развернуть на один контур одновременно
и не даёт сбросить beta под задачей, которая ещё в приёмке.
</purpose>

<why>
Stage и Production обслуживают 4-6 агентов. До введения замка два агента
могли слить свои PR и развернуть подряд, не узнав друг о друге: сверка после
развёртывания проверяет вхождение своего кода, а не отсутствие чужого.
Тот же пробел мешал сбросу beta — предусловие смотрит теги stage-ok,
а задача, находящаяся в приёмке, тега ещё не имеет.
</why>

<mechanism>
Замок — тег в origin с фиксированным именем: stage-busy для Stage,
prod-busy для Production. Ветки в имени нет.

Ветка, PR и владелец пишутся в тело тега и читаются блоком read.
</mechanism>
<why_fixed_name>
Имя обязано быть общим для всех агентов, иначе замка нет. Отказ push
возникает только при совпадении имён: с именем вида stage-busy/&lt;ветка&gt;
два агента с разными ветками ставят разные теги, оба push проходят,
и оба считают контур своим. Проверка ls-remote перед постановкой гонку
не закрывает — между проверкой и постановкой есть промежуток, ровно тот,
ради которого написан on_push_rejected.

Правило именования тега stage-ok обратное: там имя содержит ветку, потому
что тег принадлежит ветке и удостоверяет её приёмку. Замок принадлежит
контуру, а контур один. Общее имя здесь требование, а не недосмотр.
</why_fixed_name>

<why_tag>
Тег виден всем агентам сразу после git fetch и ставится одной командой.
Занятие контура атомарно: git push тега, уже существующего в origin,
отклоняется, и второй агент получает отказ, а не тихую победу.

Почему не файл-замок в репозитории: взаимное исключение он дал бы —
второй push в ту же ветку получит non-fast-forward, — но за это пришлось бы
платить коммитом, а на защищённых ветках и PR, засорять историю служебными
правками и ждать слияния там, где нужна одна команда.
</why_tag>
<why_annotated>
Тег обязан быть аннотированным, флаг -a. Лёгкий тег на тот же коммит
проходит у обоих агентов с ответом Everything up-to-date: замок не работает,
и никто об этом не узнаёт. Тело тега при этом хранит владельца, что и делает
разбор возможным.
</why_annotated>

<check>
Проверять занятость только по origin. Локальный список тегов устаревает:
чужой замок поставлен минуту назад и в вашей копии его нет.

test -z "$(git ls-remote --tags origin 'refs/tags/stage-busy')"   # Stage
test -z "$(git ls-remote --tags origin 'refs/tags/prod-busy')"    # Production

Код 0 — контур свободен.
Ненулевой код — контур занят. Прочитать тело блоком read и сверить ветку:
свой замок продолжаем, чужой разбираем блоком classify.
<why_test_z>
Голый ls-remote возвращает 0 в обоих случаях: свободен контур или занят,
видно только по напечатанным строкам. Команда, которая всегда даёт 0,
не останавливает ничего — цепочка идёт дальше независимо от вывода.
test -z переводит ответ в код возврата, и остановка происходит сама.
</why_test_z>
</check>
<merge_bound_to_lock>
Слияние PR выполняется одной командой вместе с проверкой владения замком:

  lock-acquire.sh --owned &lt;контур&gt; &lt;ветка&gt; &amp;&amp; gh pr merge &lt;номер&gt; ...

Правая часть запускается, только если левая вернула ноль. Проверка отвечает
нулём в одном случае: замок стоит в origin и ветка в его теле ваша. Чужой
замок и отсутствие замка одинаково блокируют слияние — во втором случае
потому, что контур вами не занят и его может занять другой агент.

Отдельной строкой слияние не писать. 2 сентября 2026 проверка и слияние
шли двумя строками: проверка показала занятый контур, постановка замка
отказала с already exists, а слияние всё равно выполнилось, потому что было
самостоятельной командой. Связка через &amp;&amp; делает это невозможным.
</merge_bound_to_lock>
<separate_calls>
Постановка замка и слияние — разные вызовы, и порядок между ними
обязателен: сначала занять контур, разобрать результат, и только потом
сливать связкой выше. Одной цепочкой их не выполняют, потому что между
ними стоит разбор: свой замок, чужой замок или отказ постановки ведут
к разным действиям.
</separate_calls>

<read>
Чей замок и с каких пор:

git fetch origin tag &lt;stage-busy | prod-busy&gt;
git tag -l --format='%(contents)' &lt;stage-busy | prod-busy&gt;
git for-each-ref --format='%(creatordate:iso)' refs/tags/&lt;stage-busy | prod-busy&gt;
</read>
<own_or_foreign>
Поле branch тела отвечает, чей замок. Совпадает с вашей веткой задачи —
замок ваш, работа продолжается. Не совпадает — замок чужой, дальше
блок classify. Определять принадлежность по имени тега больше нельзя:
имя у замка общее.
</own_or_foreign>
<why_creatordate>
Возраст замка берётся из объекта тега, а не из поля date его тела. Тело
пишет сам агент: поле может отсутствовать, содержать местное время или
просто быть неверным. creatordate ставит git при создании тега.
</why_creatordate>

<script>
Проверку и постановку выполняет skills/_shared/scripts/lock-acquire.sh,
вызов стоит в шаге 7 обоих деплойных скилов. Команды ниже — тот же порядок
вручную, на случай когда скрипт недоступен либо когда надо понять, что он
делает.
</script>
<acquire>
git fetch --prune --prune-tags origin        # обязательна, первой строкой

git tag -a &lt;stage-busy | prod-busy&gt; -m "Контур занят
branch: &lt;ветка задачи&gt;
pr: &lt;номер PR&gt;
agent: &lt;имя машины&gt; / &lt;кто ведёт задачу&gt;
date: &lt;дата и время UTC&gt;"
git push origin &lt;stage-busy | prod-busy&gt;
</acquire>
<agent_field>
Поле agent заполняется так, чтобы по нему можно было найти владельца:
имя машины — hostname — и человек либо задача, которая ведётся. Без этого
поле бесполезно: пользователь не поймёт, к кому идти, и единственным
исходом останется снятие замка.
</agent_field>
<why_fetch_first>
Без неё постановка падает на пустом месте, при свободном контуре:

  fatal: tag 'stage-busy' already exists          # код 128, ещё до push

Локальная копия чужого замка появляется по нашему же порядку: блок read
предписывает git fetch origin tag &lt;имя&gt;, чтобы прочитать, чей замок.
Владелец потом снимает замок в origin, а копия остаётся — обычный fetch
снятые теги не удаляет. Дальше типовой путь «занято, прочитал, дождался,
занимаю» упирается в этот отказ.

Флаг -f вместо fetch не годится: он перезапишет и настоящий чужой замок,
попавший в копию секунду назад, и агент пойдёт дальше, считая контур своим.
Отказ придёт только на push, где разбор уже другой.
Подробности — блок stale_local_tags.
</why_fetch_first>
<on_tag_failed>
git tag вернул 128 с already exists — это локальный мусор, а не занятый
контур: проверка ls-remote прошла, в origin замка нет. Выполнить
git fetch --prune --prune-tags origin и повторить постановку.
Отказ пришёл от git tag, а не от git push: разбор ниже к нему
не относится.
</on_tag_failed>
<on_push_rejected>
Отказ означает, что замок уже стоит: контур занял другой агент в промежутке
между вашей проверкой и вашей постановкой. Это штатный исход, а не сбой.
Свой локальный тег удалить — git tag -d &lt;stage-busy | prod-busy&gt; —
и остановиться, как при занятом контуре.
</on_push_rejected>
<why_local_delete>
Локальный тег остался бы и попал в следующую проверку через git tag -l,
изобразив собственный замок там, где его нет.
</why_local_delete>

<release>
Перед снятием сверить, что замок ваш:

git fetch origin tag &lt;stage-busy | prod-busy&gt;
git tag -l --format='%(contents)' &lt;stage-busy | prod-busy&gt;

Поле branch называет вашу ветку — снимать:

git tag -d &lt;stage-busy | prod-busy&gt;
git push origin :refs/tags/&lt;stage-busy | prod-busy&gt;
</release>
<why_verify_before_release>
Имя замка общее. Без сверки агент снимет чужой замок, приняв его за свой:
если его собственный замок кто-то снял, а контур успел занять третий,
команда снятия попадёт в чужой. Поле branch — единственный признак
принадлежности.
Тело называет чужую ветку — свой замок уже снят, дальше own_lock_missing.
</why_verify_before_release>
<release_order>
Снимать после того, как контур приведён в конечное состояние: на Stage —
после постановки stage-ok, в Production — после сверки и проверки критерия.
Снятый раньше замок пускает следующего агента на недоделанное.
</release_order>





<on_acceptance_failure>
Приёмка не прошла. Замок не снимается и не удерживается по решению агента:
вопрос пользователю, два исхода — освободить контур либо удержать
до исправления. Умолчание, предлагаемое первым, — освободить: правило
очереди, не получилось и встаём заново. Удержание для срочного исправления,
когда ожидание очереди дороже занятого контура.
Решено 2 сентября 2026, В-01 реестра.
</on_acceptance_failure>

пропавший свой замок, мусорные локальные теги и два разных отказа fetch.
Читать, только когда контур занят чужим замком, когда своего замка нет
на месте либо когда fetch отклонил тег замка. На успешном пути не нужен.
</ref>

<limits>
Замок держит контур, а не ветку: два агента с разными ветками не развернут
одновременно, но замок не мешает третьему читать контур и не мешает
пользователю работать в интерфейсе.
Замок не действует на агента, который его не проверяет. Защита
договорная, техническая только в атомарности постановки.
</limits>
