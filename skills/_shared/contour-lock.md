<!-- Общий файл: sma-deploy-stage и sma-deploy-prod.
     Механизм замка контура. Читается до шага, занимающего контур. -->

<purpose>
Замок контура. Не даёт двум агентам развернуть на один контур одновременно
и не даёт сбросить beta под задачей, которая ещё в приёмке.
</purpose>

<contour_lock>

<why>
Stage и Production обслуживают 4-6 агентов. До введения замка два агента
могли слить свои PR и развернуть подряд, не узнав друг о друге: сверка после
развёртывания проверяет вхождение своего кода, а не отсутствие чужого.
Тот же пробел мешал сбросу beta — предусловие смотрит теги stage-ok,
а задача, находящаяся в приёмке, тега ещё не имеет.
</why>

<mechanism>
Замок — тег в origin с фиксированным именем: stage-busy для Stage,
prod-busy для Production. Ветки в имени нет.

Ветка, PR и владелец пишутся в тело тега и читаются блоком read.
</mechanism>
<why_fixed_name>
Имя обязано быть общим для всех агентов, иначе замка нет. Отказ push
возникает только при совпадении имён: с именем вида stage-busy/&lt;ветка&gt;
два агента с разными ветками ставят разные теги, оба push проходят,
и оба считают контур своим. Проверка ls-remote перед постановкой гонку
не закрывает — между проверкой и постановкой есть промежуток, ровно тот,
ради которого написан on_push_rejected.

Правило именования тега stage-ok обратное: там имя содержит ветку, потому
что тег принадлежит ветке и удостоверяет её приёмку. Замок принадлежит
контуру, а контур один. Общее имя здесь требование, а не недосмотр.
</why_fixed_name>

<why_tag>
Тег виден всем агентам сразу после git fetch и ставится одной командой.
Занятие контура атомарно: git push тега, уже существующего в origin,
отклоняется, и второй агент получает отказ, а не тихую победу.

Почему не файл-замок в репозитории: взаимное исключение он дал бы —
второй push в ту же ветку получит non-fast-forward, — но за это пришлось бы
платить коммитом, а на защищённых ветках и PR, засорять историю служебными
правками и ждать слияния там, где нужна одна команда.
</why_tag>
<why_annotated>
Тег обязан быть аннотированным, флаг -a. Лёгкий тег на тот же коммит
проходит у обоих агентов с ответом Everything up-to-date: замок не работает,
и никто об этом не узнаёт. Тело тега при этом хранит владельца, что и делает
разбор возможным.
</why_annotated>

<check>
Проверять занятость только по origin. Локальный список тегов устаревает:
чужой замок поставлен минуту назад и в вашей копии его нет.

test -z "$(git ls-remote --tags origin 'refs/tags/stage-busy')"   # Stage
test -z "$(git ls-remote --tags origin 'refs/tags/prod-busy')"    # Production

Код 0 — контур свободен.
Ненулевой код — контур занят. Прочитать тело блоком read и сверить ветку:
свой замок продолжаем, чужой разбираем блоком classify.
<why_test_z>
Голый ls-remote возвращает 0 в обоих случаях: свободен контур или занят,
видно только по напечатанным строкам. Команда, которая всегда даёт 0,
не останавливает ничего — цепочка идёт дальше независимо от вывода.
test -z переводит ответ в код возврата, и остановка происходит сама.
</why_test_z>
</check>
<merge_bound_to_lock>
Слияние PR выполняется одной командой вместе с проверкой владения замком:

  lock-acquire.sh --owned &lt;контур&gt; &lt;ветка&gt; &amp;&amp; gh pr merge &lt;номер&gt; ...

Правая часть запускается, только если левая вернула ноль. Проверка отвечает
нулём в одном случае: замок стоит в origin и ветка в его теле ваша. Чужой
замок и отсутствие замка одинаково блокируют слияние — во втором случае
потому, что контур вами не занят и его может занять другой агент.

Отдельной строкой слияние не писать. 2 сентября 2026 проверка и слияние
шли двумя строками: проверка показала занятый контур, постановка замка
отказала с already exists, а слияние всё равно выполнилось, потому что было
самостоятельной командой. Связка через &amp;&amp; делает это невозможным.
</merge_bound_to_lock>
<separate_calls>
Постановка замка и слияние — разные вызовы, и порядок между ними
обязателен: сначала занять контур, разобрать результат, и только потом
сливать связкой выше. Одной цепочкой их не выполняют, потому что между
ними стоит разбор: свой замок, чужой замок или отказ постановки ведут
к разным действиям.
</separate_calls>

<read>
Чей замок и с каких пор:

git fetch origin tag &lt;stage-busy | prod-busy&gt;
git tag -l --format='%(contents)' &lt;stage-busy | prod-busy&gt;
git for-each-ref --format='%(creatordate:iso)' refs/tags/&lt;stage-busy | prod-busy&gt;
</read>
<own_or_foreign>
Поле branch тела отвечает, чей замок. Совпадает с вашей веткой задачи —
замок ваш, работа продолжается. Не совпадает — замок чужой, дальше
блок classify. Определять принадлежность по имени тега больше нельзя:
имя у замка общее.
</own_or_foreign>
<why_creatordate>
Возраст замка берётся из объекта тега, а не из поля date его тела. Тело
пишет сам агент: поле может отсутствовать, содержать местное время или
просто быть неверным. creatordate ставит git при создании тега.
</why_creatordate>

<script>
Проверку и постановку выполняет skills/_shared/scripts/lock-acquire.sh,
вызов стоит в шаге 7 обоих деплойных скилов. Команды ниже — тот же порядок
вручную, на случай когда скрипт недоступен либо когда надо понять, что он
делает.
</script>
<acquire>
git fetch --prune --prune-tags origin        # обязательна, первой строкой

git tag -a &lt;stage-busy | prod-busy&gt; -m "Контур занят
branch: &lt;ветка задачи&gt;
pr: &lt;номер PR&gt;
agent: &lt;имя машины&gt; / &lt;кто ведёт задачу&gt;
date: &lt;дата и время UTC&gt;"
git push origin &lt;stage-busy | prod-busy&gt;
</acquire>
<agent_field>
Поле agent заполняется так, чтобы по нему можно было найти владельца:
имя машины — hostname — и человек либо задача, которая ведётся. Без этого
поле бесполезно: пользователь не поймёт, к кому идти, и единственным
исходом останется снятие замка.
</agent_field>
<why_fetch_first>
Без неё постановка падает на пустом месте, при свободном контуре:

  fatal: tag 'stage-busy' already exists          # код 128, ещё до push

Локальная копия чужого замка появляется по нашему же порядку: блок read
предписывает git fetch origin tag &lt;имя&gt;, чтобы прочитать, чей замок.
Владелец потом снимает замок в origin, а копия остаётся — обычный fetch
снятые теги не удаляет. Дальше типовой путь «занято, прочитал, дождался,
занимаю» упирается в этот отказ.

Флаг -f вместо fetch не годится: он перезапишет и настоящий чужой замок,
попавший в копию секунду назад, и агент пойдёт дальше, считая контур своим.
Отказ придёт только на push, где разбор уже другой.
Подробности — блок stale_local_tags.
</why_fetch_first>
<on_tag_failed>
git tag вернул 128 с already exists — это локальный мусор, а не занятый
контур: проверка ls-remote прошла, в origin замка нет. Выполнить
git fetch --prune --prune-tags origin и повторить постановку.
Отказ пришёл от git tag, а не от git push: разбор ниже к нему
не относится.
</on_tag_failed>
<on_push_rejected>
Отказ означает, что замок уже стоит: контур занял другой агент в промежутке
между вашей проверкой и вашей постановкой. Это штатный исход, а не сбой.
Свой локальный тег удалить — git tag -d &lt;stage-busy | prod-busy&gt; —
и остановиться, как при занятом контуре.
</on_push_rejected>
<why_local_delete>
Локальный тег остался бы и попал в следующую проверку через git tag -l,
изобразив собственный замок там, где его нет.
</why_local_delete>

<release>
Перед снятием сверить, что замок ваш:

git fetch origin tag &lt;stage-busy | prod-busy&gt;
git tag -l --format='%(contents)' &lt;stage-busy | prod-busy&gt;

Поле branch называет вашу ветку — снимать:

git tag -d &lt;stage-busy | prod-busy&gt;
git push origin :refs/tags/&lt;stage-busy | prod-busy&gt;
</release>
<why_verify_before_release>
Имя замка общее. Без сверки агент снимет чужой замок, приняв его за свой:
если его собственный замок кто-то снял, а контур успел занять третий,
команда снятия попадёт в чужой. Поле branch — единственный признак
принадлежности.
Тело называет чужую ветку — свой замок уже снят, дальше own_lock_missing.
</why_verify_before_release>
<release_order>
Снимать после того, как контур приведён в конечное состояние: на Stage —
после постановки stage-ok, в Production — после сверки и проверки критерия.
Снятый раньше замок пускает следующего агента на недоделанное.
</release_order>

<classify>
Наткнувшись на чужой замок, собрать факты и показать их пользователю
одним сообщением. Снятие в любом случае за пользователем, агент не решает.

Что собрать:
  тело замка                      git tag -l --format='%(contents)' &lt;stage-busy | prod-busy&gt;
  возраст                         git for-each-ref --format='%(creatordate:iso)' refs/tags/&lt;stage-busy | prod-busy&gt;
  ветка существует в origin       git ls-remote --heads origin '&lt;ветка из поля branch&gt;'
  состояние PR                    gh pr list --head &lt;ветка&gt; --state all --json number,state
  что развёрнуто на контуре       ssh sma 'cd &lt;workdir контура&gt; &amp;&amp; git rev-parse HEAD'
  входит ли ветка замка           git merge-base --is-ancestor origin/&lt;ветка&gt; &lt;вершина контура&gt;

<threshold contour="stage">4 часа</threshold>
<threshold contour="production">2 часа</threshold>
<why_threshold>
Порог не снимает замок и ничего не запрещает. Он меняет только формулировку
доклада: агент говорит «похоже на брошенный» вместо «контур занят».
Production занимают ненадолго, порог там ниже.
</why_threshold>

<case name="ветки нет в origin">
Замок мусорный: задача закрыта, ветка удалена, снимать замок было некому.
Ложных срабатываний здесь не бывает. Сказать прямо и предложить снять.
</case>
<case name="ветка есть, PR слит, возраст больше порога">
Похоже на брошенный: слияние прошло, а до снятия замка агент не дошёл.
Показать факты, назвать владельца из поля agent, предложить два пути —
найти владельца либо снять замок.
</case>
<case name="ветка есть, PR открыт">
Агент остановился между постановкой замка и слиянием. Контур при этом чист:
его код в beta не попал, снятие замка последствий не имеет. Самый безобидный
случай, но решение всё равно за пользователем.
</case>
<case name="возраст меньше порога">
Контур занят, идёт работа. Ждать. Ничего не предлагать.
</case>

<contour_state>
В докладе показывать и состояние контура: входит ли ветка замка в развёрнутую
вершину. Входит — код брошенной задачи лежит на контуре, и снятие замка его
оттуда не убирает: следующее развёртывание пойдёт поверх. Тогда решается
не только судьба замка, но и нужен ли сброс beta.
</contour_state>
</classify>

<foreign_lock>
Чужой замок агент не снимает по своему решению. Ни при каких обстоятельствах,
включая полную уверенность, что владелец о нём забыл.
Порядок: собрать факты блоком classify, показать пользователю, ждать команды.
Снятие выполняется только по явной команде и сопровождается блоком lock_void.
<why>
Снятие пускает следующего агента на контур, который может быть занят
по-настоящему. Признак «брошенный» — вероятностный, а последствия ошибки
приходятся на живого владельца.
</why>
</foreign_lock>

<lock_void>
<when>Пользователь распорядился снять чужой замок.</when>
<command>
git tag -a lock-void/&lt;ветка из поля branch&gt; -m "Чужой замок снят
lock: &lt;stage-busy | prod-busy&gt;
owner: &lt;поле agent из тела снятого замка&gt;
age: &lt;возраст на момент снятия&gt;
reason: &lt;почему сочли брошенным&gt;
by: &lt;кто снял&gt;
date: &lt;дата и время UTC&gt;"
git push origin lock-void/&lt;ветка из поля branch&gt;

git push origin :refs/tags/&lt;stage-busy | prod-busy&gt;
</command>
<why_branch_in_name>
Имя lock-void содержит ветку, в отличие от самого замка. Столкновение имён
здесь не нужно и вредно: запись адресована конкретному владельцу, и он ищет
её по имени своей ветки. Двум снятым замкам разных веток нужны две записи.
</why_branch_in_name>
<order>
Сначала поставить lock-void, потом снять замок. Обратный порядок оставляет
промежуток, в котором контур свободен, а объяснения не существует.
</order>
<why>
Владелец, если он жив, вернётся и не найдёт своего замка. Без записи он
не отличит собственную ошибку от чужого вмешательства и может продолжить
работу на контуре, который уже занят третьим агентом.
</why>
<cleanup>
Тег lock-void снимает тот, кто его ставил, после того как владелец
объявился либо стало ясно, что не объявится. Удаление тега — вопрос
пользователю.
</cleanup>
</lock_void>

<own_lock_missing>
<when>
Агент дошёл до снятия своего замка, а замка в origin нет — либо замок есть,
но поле branch его тела называет чужую ветку. Второе означает то же самое:
своего замка нет, а контур успел занять другой агент.
</when>
<action>
Остановиться. Не считать это мелочью и не продолжать работу на контуре.
Чужой замок, оказавшийся на месте своего, не снимать.
Проверить, не снимал ли замок кто-то другой:

git ls-remote --tags origin 'refs/tags/lock-void/&lt;ветка&gt;'
git fetch origin tag lock-void/&lt;ветка&gt;
git tag -l --format='%(contents)' lock-void/&lt;ветка&gt;

Тег есть — замок сняли, причина в теле. Контур мог быть занят другим
агентом после снятия: проверить занятость блоком check и показать
пользователю обе записи.
Тега нет — замок исчез необъяснимо. Сообщить пользователю, дальше
не работать с контуром.
</action>
</own_lock_missing>

<on_acceptance_failure>
Приёмка не прошла. Замок не снимается и не удерживается по решению агента:
вопрос пользователю, два исхода — освободить контур либо удержать
до исправления. Умолчание, предлагаемое первым, — освободить: правило
очереди, не получилось и встаём заново. Удержание для срочного исправления,
когда ожидание очереди дороже занятого контура.
Решено 2 сентября 2026, В-01 реестра.
</on_acceptance_failure>

<not_covered>
<item>
Автоматического снятия брошенных замков нет и не планируется. Признак
вероятностный, решение остаётся за пользователем — блоки classify
и foreign_lock. Следствие: пока пользователь не ответил, контур занят.
</item>
<where>Реестр: _claude/tasks/git-flow/open-questions.md.</where>
</not_covered>

<stale_local_tags>
Локальные теги замков надо вычищать: git fetch --prune --prune-tags origin.
Обычный fetch снятые в origin теги не удаляет, они копятся в каждой копии.
Мест, где это обязательно, два: перед постановкой замка, блок acquire,
и в каталоге развёртывания, шаг 8 обоих скилов.

Отдельный случай — переход с прежней схемы имён stage-busy/&lt;ветка&gt;
на фиксированное имя. Пока старый тег жив, тег с именем stage-busy создать
нельзя: имя ссылки не может быть префиксом имени другой ссылки.

Текст отказа зависит от того, как хранятся ссылки, а не от сути:

  распакованные:  cannot lock ref 'refs/tags/stage-busy':
                  'refs/tags/stage-busy/&lt;ветка&gt;' exists;
                  cannot create 'refs/tags/stage-busy'
  упакованные:    'refs/tags/stage-busy/&lt;ветка&gt;' exists;
                  cannot create 'refs/tags/stage-busy'

Отказ валит весь fetch, а не одну ссылку: не обновляются ни ветки, ни теги.
Лечится удалением старого тега — git tag -d stage-busy/&lt;ветка&gt; — либо
тем же --prune-tags, если в origin его уже нет.
<why_not_directory>
Распакованная ссылка со слешем в имени — это файл в подкаталоге
.git/refs/tags/stage-busy/, и кажется, что мешает именно каталог. Каталог
здесь следствие способа хранения, а не причина. После git pack-refs --all
распакованных файлов не остаётся вовсе, ссылка лежит строкой в packed-refs,
каталога на диске нет — создание тега всё равно отклоняется. Проверено
запуском 2 сентября 2026.
Практическое следствие: искать и удалять каталог руками бесполезно, лечит
только удаление ссылки командой git.
</why_not_directory>
<scope>
Каталог, если он есть, лежит внутри .git каталога развёртывания. В рабочее
дерево ничего не попадает, git status его не видит, правило о каталоге
развёртывания он не нарушает. Ломается другое: fetch в этом каталоге,
из-за чего каталог отстаёт от вершины ветки — то, что ловят сверки
шага 10 Stage и шага 9 Production.
</scope>
Проверено 2 сентября 2026 в /opt/sma-beta.
<clobber_not_error>
Второй отказ, внешне похожий на первый и ошибкой не являющийся. В каталоге
развёртывания лежит копия замка, снятая с origin раньше, а в origin под тем же
именем стоит замок другого агента: объекты разные, и fetch печатает

  ! [rejected]  stage-busy -&gt; stage-busy  (would clobber existing tag)

Флаг --prune-tags здесь не срабатывает: он удаляет теги, которых в origin
нет, а этот есть. Обновить существующий тег на другой объект fetch без --force
