# Настройки, которые выполняет Игорь

Три раздела. Первый — на GitHub, второй — учётные записи и токены агентов,
третий — на сервере под root.

Каждый раздел заканчивается проверкой. Прислать вывод проверок.

<task id="1" name="защита ветки prod">

<who>Владелец репозитория. Раздел Settings соавторам недоступен.</who>

<context>
Репозиторий igormahachkala/servicemanager-ai-2.0 принадлежит личной учётной
записи. У таких репозиториев два уровня доступа: владелец и соавтор. Ролей
Admin, Maintain, Triage у них нет, выдать их нельзя.

Сейчас порядок работы существует как текст в skills/. Настройка GitHub его
не подкрепляет: участник с правом записи может отправить коммит прямо в prod.
</context>

<step id="1.1" name="открыть настройки">
Settings → Branches → Add branch protection rule
Либо Settings → Rules → Rulesets, если интерфейс предлагает этот путь.
</step>

<step id="1.2" name="шаблон имени">
Branch name pattern: prod
<constraint>Ровно prod. Не prod/*, не маска.</constraint>
</step>

<step id="1.3" name="требование PR">
Require a pull request before merging — включить.
  Require approvals — снять галочку либо выставить 0.
<why>
Работают нейросети, человек PR не одобряет. Требование одобрений остановит
поток целиком: агенты не смогут слить ни одного PR.
</why>
</step>

<step id="1.4" name="требование актуальности">
Require status checks to pass before merging — включить.
  Список проверок оставить пустым: CI пока нет.
  Require branches to be up to date before merging — включить.
<why>
Требование актуальности доступно только как подпункт требования проверок,
поэтому верхняя галочка включается даже при пустом списке.

Смысл: одновременно работают 4-6 агентов двух разработчиков. Пока агент
проверяет своё изменение, целевая ветка уходит вперёд, и проверенное
состояние устаревает. Настройка не даёт слить непроверенное.
</why>
<not_yet_effective>
Установлено 2026-08-31 при настройке: GitHub пишет под этой галочкой
«This setting will not take effect unless at least one status check is
enabled». Список проверок пуст, значит требование актуальности включено,
но не действует.

Галочку оставить: заработает сама, когда появится CI. Но считать, что
защита от слияния устаревшего состояния уже есть, нельзя. Пока правило
даёт три вещи: слияние только через PR, запрет force push, запрет удаления.
</not_yet_effective>
</step>

<step id="1.5" name="разрушающие операции">
Allow force pushes — выключено.
Allow deletions — выключено.
<note>Обе выключены по умолчанию, проверить, что так и осталось.</note>
</step>

<step id="1.6" name="решение о владельце">
Do not allow bypassing the above settings — вопрос к Игорю.

Включено: правила действуют и на владельца, prod строгий без исключений.
Порядок работы это допускает: откат Production делается revert-PR,
а не прямым push.

Выключено: у владельца остаётся ручной обход.

Рекомендация — включить. Решает Игорь.
</step>

<do_not>
<f>Не защищать ветку beta. Это сделано намеренно.</f>
<why>
beta расходная: после каждого релиза её сбрасывают до состояния prod
командой git push --force-with-lease. Через PR force push не делается.
Защита beta наравне с prod отменила бы очистку контура, и beta накопила бы
отброшенные задачи. Граница beta проведена правилом в
skills/git-workflow.md, блок branch_status.
</why>
<f>Не включать требование одобрений на prod, см. шаг 1.3.</f>
<f>Не добавлять обязательные status checks: CI ещё нет, поток встанет.</f>
</do_not>

<verify>
gh api repos/igormahachkala/servicemanager-ai-2.0/branches/prod/protection

Ожидается:
  required_pull_request_reviews присутствует,
    required_approving_review_count = 0
  required_status_checks присутствует, strict = true, contexts пустой
  allow_force_pushes.enabled = false
  allow_deletions.enabled = false

gh api repos/igormahachkala/servicemanager-ai-2.0/branches/beta/protection

Ожидается 404 Branch not protected. Это правильный ответ, не ошибка.
</verify>

</task>

<task id="2" name="учётные записи и токены агентов">

<who>Игорь как владелец репозитория. Токены создаёт владелец учётной записи, под которой работает агент.</who>

<question>
Под какими учётными записями GitHub работают агенты Игоря. Ответ нужен
до выдачи токенов.

Личные токены каждого участника дают прослеживаемость: в истории PR видно,
кто именно слил. Отдельная служебная учётная запись проще в выдаче и отзыве,
но обезличивает действия — шесть агентов под одним именем, разобрать потом
нечего.

Решение за Игорем. Прислать ответ.
</question>

<step id="2.1" name="создать токен">
GitHub: Settings → Developer settings → Personal access tokens
→ Tokens (classic) → Generate new token (classic).

Отметить:
  repo        — первая строка списка, включает пять вложенных областей
  workflow    — отдельная строка под группой repo
  read:org    — внутри группы admin:org, только её; write:org и admin:org
                не отмечать

Остальное не отмечать.

<why_classic>
Установлено 2026-08-31 на практике.

Fine-grained токен здесь не годится тому, кто не владеет репозиторием:
он работает только с репозиториями выпустившего его аккаунта. Соавтор
в списке репозиториев чужого владельца просто не увидит. Вариант
«Public repositories» в fine-grained даёт доступ только на чтение —
push и создание PR им не сделать.

Владелец репозитория может выпустить fine-grained, но проще держать один
порядок для всех: classic работает и у владельца, и у соавторов.
</why_classic>
<why_three_scopes>
gh при входе проверяет ровно три области: repo, read:org, workflow.
Без любой из них gh auth login отказывает с сообщением
error validating token: missing required scope.

read:org и workflow самому потоку не нужны, это требование gh.
</why_three_scopes>
<note_private>
Область repo, а не public_repo: репозиторий планируется перевести
в закрытый. С public_repo токен в день перевода перестанет работать,
и отказ будет выглядеть как 404, будто репозитория нет.
</note_private>
<note_scope>
Classic-токен действует на все репозитории, к которым у выпустившего есть
доступ. Выбор репозитория в нём не предусмотрен. Разница между repo
и public_repo — только во включении закрытых.
</note_scope>
</step>

<step id="2.2" name="срок годности">
Записать дату истечения токена и порядок продления.
<why>
По истечении поток встанет на создании PR у всех агентов сразу, и отказ
будет выглядеть как 403 — неотличимо от нехватки прав.
</why>
</step>

<step id="2.3" name="передать агенту">
gh auth login

Ответы: GitHub.com → HTTPS → Authenticate Git with your GitHub credentials: Yes
→ Paste an authentication token → вставить значение.

<constraint>
Не передавать значение аргументом командной строки и не вставлять
в переписку — попадёт в историю оболочки и в логи.
</constraint>
<note>
Область токена можно дополнить, не создавая новый: открыть его на странице
Tokens (classic), отметить недостающее, Update token. Значение при этом
не меняется.
</note>
</step>

<verify>
gh auth status
gh api repos/igormahachkala/servicemanager-ai-2.0/pulls --jq 'length'

Первая: Logged in to github.com.
Вторая: число. Она проверяет право на PR до того, как агент дойдёт
до создания PR в потоке. Запрос читающий, ничего не создаёт.

403 на второй — нет права Pull requests: Read and write.
404 — нет доступа к репозиторию либо токен выдан на другой репозиторий.
</verify>

</task>

<task id="3" name="доступ к серверу">

<who>root на сервере 194.67.101.37.</who>

<context>
Сейчас агенты Игоря ходят под root с отдельными ключами. Под root ограничения
из skills/deploy-*.md не имеют технической силы: можно развернуть контур
из произвольного каталога и обойти любую проверку.

Перевод на пользователя deploy делает правила исполнимыми, а не
декларативными.
</context>

<state name="уже настроено">
Пользователь deploy существует, состоит в группе docker, владеет каталогами
/opt/sma-prod, /opt/sma-beta и /var/backups/sma, читает файлы окружения.
Порядок проверки — skills/agent-setup.md, часть A, блок verify_server.
</state>

<step id="3.1" name="ключи агентов Игоря">
Каждый агент генерирует свою пару на своей машине по
skills/agent-setup.md, часть B, шаг 1, и отдаёт публичный ключ.

Публичные ключи добавляются в /home/deploy/.ssh/authorized_keys:

echo '<строка публичного ключа>' >> /home/deploy/.ssh/authorized_keys
chown deploy:deploy /home/deploy/.ssh/authorized_keys
chmod 600 /home/deploy/.ssh/authorized_keys

<constraint>
Комментарий ключа должен опознавать владельца: codex-deploy@sma,
cursor-deploy@sma и так далее. Иначе отзыв доступа станет угадыванием.
</constraint>
<constraint>
ssh-copy-id здесь не работает: у deploy нет пароля, аутентифицироваться
для первой записи нечем.
</constraint>
</step>

<step id="3.2" name="отпечаток хоста">
Агенту нужен отпечаток, чтобы сверить его с тем, что придёт по сети:

ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

Передать строку агенту любым каналом, кроме самого ssh-подключения:
смысл сверки в том, что источник независим.
</step>

<step id="3.3" name="убрать ключи агентов из root">
После того как агенты подтвердят работу под deploy, удалить их ключи
из /root/.ssh/authorized_keys. Личный ключ Игоря оставить.
<constraint>Не выполнять до подтверждения, иначе агенты потеряют доступ.</constraint>
</step>

<step id="3.4" name="ключи закрытых задач">
В /root/.ssh/authorized_keys числятся два ключа, выданные под релизную
задачу от 5 августа и не отозванные:

  sma-release-stage-prod-001-2026-08-05
  sma-release-stage-prod-001-retry-2026-08-05

Задача закрыта. Удаление — решение Игоря.
</step>

<verify>
ssh sma 'whoami; id -nG'
  → deploy, в группах присутствует docker

awk '{print $1, $3}' /home/deploy/.ssh/authorized_keys
  → тип ключа и комментарий по каждому агенту. Значения ключей не печатает.

awk '{print $1, $3}' /root/.ssh/authorized_keys
  → после шага 3.3 остаётся только личный ключ Игоря.
</verify>

</task>
