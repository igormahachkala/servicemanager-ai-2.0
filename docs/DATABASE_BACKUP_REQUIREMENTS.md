# Требования: резервное копирование, восстановление, удержание, оповещения

Документ фиксирует **требования**, а не достигнутое состояние. Относится к
issue #378.

> **Текущий статус: НЕ ПОДТВЕРЖДЕНО.**
>
> В репозитории нет ни механизма резервного копирования, ни записей о прогонах
> восстановления. Ни один пункт ниже не может считаться выполненным до
> фактического прогона с зафиксированными результатами. Наличие этого документа
> ничего не доказывает.

---

## Что уже известно о контуре

Из `docker-compose.yml`:

- PostgreSQL 16, данные в именованном томе `postgres_data`;
- `uploads` смонтирован как bind mount `./uploads:/app/uploads` — то есть
  вложения лежат **вне** базы, и копия базы их не содержит;
- отчёты MAX: `/opt/maxbot_reports` — тоже вне базы;
- `healthcheck` не задан ни одному сервису;
- `depends_on: postgres` указан без условия готовности, поэтому бэкенд
  стартует до готовности базы и полагается на `prisma migrate deploy`.

Последние два пункта — предмет раздела «Интеграция с Docker» ниже.

## 1. Автоматические резервные копии базы

Требования:

| № | Требование |
|---|---|
| 1.1 | Копии создаются по расписанию, без участия человека |
| 1.2 | Периодичность согласована с владельцем и зафиксирована (см. RPO) |
| 1.3 | Используется `pg_dump`/`pg_basebackup` с версией клиента, совпадающей с сервером (PostgreSQL 16) |
| 1.4 | Копия пишется **вне** хоста приложения: отказ диска не должен уносить и данные, и копии |
| 1.5 | Копии шифруются при хранении, доступ ограничен |
| 1.6 | Факт и результат каждого запуска наблюдаемы (см. раздел 5) |
| 1.7 | Проверяется целостность артефакта, а не только код выхода (например, `pg_restore --list`) |

Чего делать нельзя: хранить копии в том же томе, что и данные; складывать
дампы в репозиторий; выполнять копирование на работающем контуре без
согласования окна.

## 2. Резервное копирование uploads

| № | Требование |
|---|---|
| 2.1 | `uploads` копируются отдельно от базы — они в ней не лежат |
| 2.2 | Копия согласована по времени с копией базы, иначе ссылки на вложения будут указывать в пустоту |
| 2.3 | `/opt/maxbot_reports` включён в охват либо явно признан невосстанавливаемым |
| 2.4 | Периодичность и удержание те же, что у базы, если владелец не решит иначе |

## 3. Прогон восстановления (restore drill)

| № | Требование |
|---|---|
| 3.1 | Восстановление выполняется в **изолированное** окружение, не на Stage и не на Production |
| 3.2 | Прогон проводится из реальной свежей копии, а не из специально подготовленной |
| 3.3 | Фиксируются: дата, идентификатор копии, время начала и завершения, достигнутые RPO и RTO |
| 3.4 | После восстановления проверяется работоспособность: `prisma migrate status`, `GET /health/ready` → 200, выборочная сверка данных |
| 3.5 | Проверяется связность вложений: восстановленные записи ссылаются на существующие файлы |
| 3.6 | Производственные данные в прогоне используются только по согласованной процедуре обращения с ними |
| 3.7 | Результат прогона фиксируется письменно; «прогон прошёл» без цифр RPO/RTO результатом не считается |

Периодичность прогонов согласуется с владельцем. Копия, из которой ни разу не
восстанавливались, резервной копией не является.

## 4. Удержание копий

| № | Требование |
|---|---|
| 4.1 | Глубина удержания задана явно (например, N суточных, M недельных, K месячных) |
| 4.2 | Удаление старых копий автоматическое и предсказуемое |
| 4.3 | Удержание согласовано с требованиями к данным и согласовано владельцем |
| 4.4 | Удаление копий логируется |

## 5. Оповещения

| № | Требование |
|---|---|
| 5.1 | Оповещение при **невыполнении** запуска копирования |
| 5.2 | Оповещение при устаревании последней успешной копии дольше допустимого |
| 5.3 | Оповещение при `GET /health/ready` ≠ 200 дольше заданного порога |
| 5.4 | Оповещение при исчерпании места под данными и под копиями |
| 5.5 | Указан адресат и порядок эскалации к владельцу |
| 5.6 | Отсутствие оповещений не считается подтверждением исправности: требуется положительный признак свежести копии |

Пункт 5.6 — ключевой. Молчащий мониторинг и исправная система выглядят
одинаково.

## Интеграция с Docker

Оценка (инфраструктуру этот PR не меняет):

1. **Healthcheck у backend.** Сейчас нет. Предлагается использовать новый
   маршрут готовности:

   ```yaml
   backend:
     healthcheck:
       test: ["CMD-SHELL", "wget -qO- http://127.0.0.1:3000/health/ready || exit 1"]
       interval: 30s
       timeout: 5s
       retries: 3
       start_period: 60s
   ```

   `start_period` обязателен: на старте выполняется `prisma migrate deploy`,
   и до его завершения готовности нет закономерно.

   Важное предупреждение: при `restart: unless-stopped` healthcheck сам по
   себе контейнер не перезапускает, но оркестратор или внешний наблюдатель
   может это делать. Перезапуск бэкенда из-за недоступной базы бесполезен и
   создаёт цикл. Поэтому если перезапуск по healthcheck будет включён, он
   должен опираться на **liveness** (`/health`), а не на готовность.

2. **Healthcheck у postgres.** Сейчас нет. Предлагается `pg_isready`, и тогда
   `depends_on` для бэкенда можно задать с `condition: service_healthy` —
   это устранит текущий старт бэкенда раньше готовности базы.

3. **Разделение ролей.** `/health` — для принятия решения о перезапуске,
   `/health/ready` — для решения о подаче трафика и для мониторинга.

Изменения в `docker-compose.yml` в этом PR **не вносились**: это живая
инфраструктура, и правка требует отдельного согласования и окна.

## Интеграция с мониторингом

Без изменения живой инфраструктуры:

1. Внешняя проверка `GET /health/ready` с интервалом 30–60 секунд, порог
   оповещения — две подряд неудачи (кэш результата на стороне приложения — 1
   секунда, поэтому опрос не создаёт нагрузки).
2. Отдельная проверка liveness `GET /health` — чтобы различать «процесс лёг» и
   «база недоступна».
3. Признак свежести копии как отдельная метрика. Маршрут готовности её
   намеренно не включает: смешивать состояние приложения и доказательство
   резервного копирования нельзя — иначе недоступность копий будет выглядеть
   как неработающее приложение, и наоборот.
4. Панель дежурного: liveness, readiness, возраст последней успешной копии,
   свободное место, статус миграций.

## Как закрывать issue #378

Для каждого пункта нужно **фактическое** свидетельство:

- расписание копирования — запуски видны в журнале за период;
- удержание — зафиксировано и наблюдается фактическое удаление старых копий;
- прогон восстановления — выполнен в изолированном окружении, записаны RPO и
  RTO;
- наблюдаемость — проверки готовности и свежести копий заведены, порог
  оповещения сработал на учебном отказе;
- эскалация — адресат назван, порядок описан.

Код, добавленный этим PR, закрывает только одну строчку из списка:
наблюдаемость готовности PostgreSQL. Остальное — операционная работа с
доступом к инфраструктуре, и помечать её выполненной по факту наличия
документа нельзя.
