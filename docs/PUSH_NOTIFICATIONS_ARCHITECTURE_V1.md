# Push Notifications Architecture V1

**Исследовательский документ для согласования с management-потоком.**
Дата: 2026-07-08 · Автор: mobile-поток · Статус: research / proposal (кода нет)

> **Зона:** backend-часть (сущности, очередь, доставка, VAPID, воркеры) — **shared zone**, требует согласования и реализации с management-потоком. Frontend-часть (Service Worker, подписка, UX разрешения, тумблеры) — mobile-поток по готовности контракта.

---

## 0. Резюме (TL;DR)

**Можно ли, чтобы техник получал уведомления как в Telegram/WhatsApp, когда PWA `/m` закрыта?**

- **Android / Chrome / десктоп:** ✅ **Да, полноценно.** Web Push работает в фоне при закрытом приложении, без установки, из обычного браузера. Практически паритет с нативом.
- **iPhone (iOS/iPadOS):** ⚠️ **Да, но с жёсткими условиями Apple.** Web Push на iOS работает **только** если PWA **установлена на домашний экран** (Add to Home Screen) и открывается в standalone-режиме; требуется **iOS 16.4+** (март 2023). В обычной вкладке Safari на iPhone push **невозможен вообще**. Доставка менее надёжна, чем у нативных приложений (подписки могут «пропадать»). Полностью нативного поведения без App Store добиться нельзя — но при установленной PWA закрытый-app push **реально работает**.

**Вывод:** цель достижима на всех платформах через стандартный **Web Push (VAPID)**. Ключевое условие для iPhone — довести пользователя до установки PWA на домашний экран. Чат-сообщения (главный сценарий, см. §6) при закрытом приложении доставляются push'ем на всех платформах при соблюдении этого условия.

## 1. Совместимость (самый важный раздел)

Транспорт везде — стандартный **Web Push API + VAPID** (браузер сам маршрутизирует в APNs на Apple и в FCM на Android; **разработчик APNs/FCM напрямую не трогает**).

| Платформа | Push при закрытом app | Условие | Версия | Примечания |
|---|---|---|---|---|
| **Android Chrome** | ✅ да | ничего (даже без установки) | давно | полноценно, богатые уведомления |
| **Android (Firefox/Edge/Samsung)** | ✅ да | — | давно | ок |
| **Desktop Chrome/Edge/Firefox** | ✅ да | — | давно | ок |
| **iPhone/iPad Safari — вкладка** | ❌ **нет** | — | — | Web Push в браузерной вкладке на iOS **не поддерживается** |
| **iPhone/iPad — PWA на домашнем экране** | ✅ да | **обязательно Add to Home Screen** | **iOS/iPadOS 16.4+** | работает, но ниже надёжность; подписки могут теряться |
| **macOS Safari** | ✅ да | вкладка ИЛИ установленное web-app | Safari 16+ / 18.5 declarative | на Mac даже в обычной вкладке |

**Критично для iPhone:**
- **Только home-screen PWA.** Пользователь должен вручную: Safari → «Поделиться» → «На экран „Домой"». Автоматического промпта установки на iOS **нет** — нужен свой онбординг-гайд.
- **Все браузеры на iOS = WebKit.** Chrome/Firefox на iPhone используют движок Safari → те же ограничения; отдельного пути нет.
- **Разрешение — только по жесту пользователя.** `Notification.requestPermission()` обязан вызываться из обработчика клика; вызов на загрузке страницы iOS **молча игнорирует**.
- **EU-нюанс (исторический):** в iOS 17.4 Apple кратко грозила убрать PWA-поддержку в ЕС, затем **откатила** — PWA push в ЕС снова доступен. Для РФ-аудитории неактуально, отмечено для полноты.

## 2. Современный подход: классический vs Declarative Web Push

Есть **два** механизма — заложим оба.

### 2а. Классический Web Push (Service Worker)
- SW обязателен: событие `push` → SW через `showNotification()` рисует уведомление.
- Максимальная гибкость (кастомный рендер, actions, дедуп, группировка, badge). **Единственный путь для богатых чат-уведомлений с группировкой.**
- Поддержка: везде, где есть Web Push (в т.ч. iOS 16.4+ home-screen PWA).

### 2б. Declarative Web Push (без Service Worker) — новое (2025)
- **Safari 18.4 / iOS 18.4 (март 2025)** ввели упрощённый механизм: сервер шлёт готовый JSON, браузер сам показывает уведомление **без SW**. W3C уже включил это в основную спецификацию Push API.
- Формат payload:
  ```json
  {
    "web_push": 8030,
    "notification": {
      "title": "Фудзияма Арбат · Заявка #4521",
      "body": "Михаил: Кондиционер всё ещё не работает, нужна помощь",
      "navigate": "https://servicemanagerai.ru/m/tickets/4521?tab=chat",
      "silent": false,
      "app_badge": "3"
    }
  }
  ```
- SW **опционален**: если зарегистрирован — может перехватить `PushEvent` и заменить контент (группировка/локализация); если нет или упал — показывается декларативный fallback.
- **Плюс для нас:** повышает надёжность на iOS (меньше движущихся частей) и даёт graceful degradation.

**Рекомендация:** реализовать **гибрид** — SW для богатых уведомлений (группировка чата, actions) + декларативный fallback (`web_push: 8030` + `navigate`), чтобы на новых iOS работало даже если SW выгружен. Backend должен уметь слать оба формата в одном push (declarative-поля игнорируются старыми клиентами, SW-логика — новыми декларативными).

## 3. Архитектура (схема потока)

```
[Событие в системе]  (новое сообщение в чате / назначение / SLA …)
        │
        ▼
[Backend: NotificationDispatcher]
   ├─ определить получателей (по заявке/объекту/роли)
   ├─ проверить пользовательские настройки (тумблеры типов)
   ├─ собрать payload (title/body-превью/navigate/collapse-key)
   └─ поставить задачи в очередь (по одной на каждое устройство)
        │
        ▼
[Очередь: BullMQ/Redis  (или pg-boss на Postgres)]
        │
        ▼
[Push-воркеры (stateless, масштабируются)]
   ├─ web-push (VAPID-подпись + шифрование payload под подписку)
   ├─ POST на subscription.endpoint (push-сервис Apple/Google)
   ├─ 201 → успех
   ├─ 404/410 Gone → пометить подписку невалидной / удалить
   └─ 429/5xx → retry с backoff
        │
        ▼
[Push-сервис платформы: APNs (Apple) / FCM (Google) / Mozilla]
        │
        ▼
[Устройство: Service Worker.onpush → showNotification()
             (или Declarative fallback)]
        │
        ▼
[Тап по уведомлению → navigate → /m/tickets/:id?tab=chat  (deep-link в тред)]
```

**Frontend ↔ Backend контур подписки:**
```
PWA: register SW → requestPermission (по клику) → pushManager.subscribe(VAPID pub)
   → POST /push/subscriptions {endpoint, keys, deviceMeta}  → сохранили
```

## 4. Backend (сущности, API, очередь) — shared zone

### 4.1. Схема данных (черновые Prisma-модели)

```prisma
model PushSubscription {
  id           String   @id @default(uuid())
  userId       String
  companyId    String
  endpoint     String   @unique          // URL push-сервиса (Apple/Google)
  p256dh       String                     // ключ шифрования (из subscription.keys.p256dh)
  auth         String                     // auth-секрет (из subscription.keys.auth)
  platform     String?                    // 'ios-pwa' | 'android' | 'desktop'
  userAgent    String?
  declarative  Boolean  @default(false)   // поддерживает ли клиент Declarative Web Push
  createdAt    DateTime @default(now())
  lastSeenAt   DateTime @default(now())   // обновляем при заходе — для очистки протухших
  failCount    Int      @default(0)       // счётчик подряд ошибок доставки
  disabledAt   DateTime?                  // мягкое отключение после 410/N ошибок

  @@index([userId])
  @@index([companyId])
}

model PushPreference {
  id        String  @id @default(uuid())
  userId    String  @unique
  // тумблеры по типам (см. §7). Дефолты: чат/назначения/SLA — ON; новости — OFF.
  chat            Boolean @default(true)   // сообщения в чатах (главный сценарий)
  ticketNew       Boolean @default(true)
  assignment      Boolean @default(true)
  statusChange    Boolean @default(true)
  acceptance      Boolean @default(true)   // готово к приёмке / принято
  acceptanceReject Boolean @default(true)  // отклонение приёмки → доработка
  sla             Boolean @default(true)   // предупреждение/просрочка
  news            Boolean @default(false)  // рассылки/новости
  quietHoursFrom  Int?                     // опц. «не беспокоить» (час 0–23)
  quietHoursTo    Int?
}

// опц. журнал доставки — для аналитики/дедупа (можно вынести в отдельную БД/ttl)
model PushDeliveryLog {
  id             String   @id @default(uuid())
  subscriptionId String
  eventType      String
  entityId       String?
  status         String   // queued | sent | failed | expired
  createdAt      DateTime @default(now())
  @@index([subscriptionId, createdAt])
}
```

Хранение секретов VAPID (public/private) — в env/secret-manager, не в БД.

### 4.2. API (endpoints)

```ts
// Подписка/устройства
GET    /push/vapid-public-key            → { key: string }   // публичный VAPID-ключ для фронта
POST   /push/subscriptions               // { endpoint, keys:{p256dh,auth}, platform, declarative }
DELETE /push/subscriptions               // { endpoint }  — отписка/logout этого устройства
POST   /push/subscriptions/heartbeat     // { endpoint }  — обновить lastSeenAt

// Настройки
GET    /push/preferences                 → PushPreference
PATCH  /push/preferences                 // частичный апдейт тумблеров

// Диагностика/QA
POST   /push/test                        // отправить тестовый push на устройства текущего юзера
```

### 4.3. Очередь / воркеры / надёжность

- **Очередь:** BullMQ (Redis) либо `pg-boss` (Postgres — без новой инфры, если Redis нежелателен). По одной задаче на устройство (fan-out на этапе диспетчера).
- **Воркеры:** stateless, горизонтально масштабируются; используют Node-библиотеку `web-push` (VAPID-подпись + RFC 8291 шифрование payload под каждую подписку).
- **Retry:** экспоненциальный backoff на `429`/`5xx`/сеть; ограниченное число попыток.
- **Очистка невалидных:** `404`/`410 Gone` от push-сервиса → `disabledAt`/удаление подписки. Плюс TTL-чистка по `lastSeenAt` (устройство не заходило > N недель — на iOS хранилище может очищаться, подписка мертва).
- **Дедуп/коллапс:** `collapse-key`/`Topic`-заголовок (или `tag` в уведомлении) — чтобы серия сообщений одного чата схлопывалась, а не спамила N раз (мессенджер-поведение).
- **Идемпотентность:** ключ события (eventType+entityId+messageId) — не слать один и тот же push дважды при ретраях диспетчера.

## 5. Frontend (Service Worker, подписка) — mobile-поток

- **Регистрация SW:** `navigator.serviceWorker.register('/m/sw.js')` — один SW на PWA; в нём обработчики `push`, `notificationclick`, `pushsubscriptionchange`.
- **Запрос разрешения — строго по жесту** (кнопка «Включить уведомления»), иначе iOS игнорирует.
- **Подписка:**
  ```js
  const reg = await navigator.serviceWorker.ready
  const sub = await reg.pushManager.subscribe({
    userVisibleOnly: true,
    applicationServerKey: <VAPID public key>,
  })
  await api.post('/push/subscriptions', { endpoint: sub.endpoint, keys: sub.toJSON().keys, platform, declarative: 'pushManager' in window })
  ```
- **Обновление/пересоздание:** слушать `pushsubscriptionchange` в SW → переподписаться и отправить новую подписку (важно на iOS, где подписки «пропадают»).
- **Удаление устройства:** при logout — `sub.unsubscribe()` + `DELETE /push/subscriptions`.
- **`notificationclick`:** `clients.openWindow(navigate)` / фокус существующего окна → deep-link в тред заявки/объекта (`/m/tickets/:id?tab=chat` или `/m/chats/:objectId`).
- **Heartbeat:** при каждом заходе в PWA обновлять `lastSeenAt` (для очистки протухших).

## 6. События (что шлём push'ем)

### 🔵 6.0. ЧАТ-СООБЩЕНИЯ — первоклассный, ГЛАВНЫЙ сценарий

> Игорь: **«чат — основная рабочая зона»**. Push по чату — не второстепенное уведомление, а **ключевой use-case**. Должен работать при **закрытом** приложении на всех платформах (на iPhone — при установленной PWA).

Сообщения в **тредах заявок** И в **тредах объектов** (см. стратегическое направление «Чат до уровня Telegram»):
- **Превью текста** в теле уведомления: `«Михаил · Фудзияма Арбат: Кондиционер всё ещё греет»` (имя автора + чат + начало сообщения).
- **Deep-link прямо в тред:** тап → `/m/tickets/:id?tab=chat` (заявка) или `/m/chats/:objectId` (объект), к нужному сообщению.
- **Группировка по чату** (мессенджер-стиль): несколько сообщений одного треда — одно схлопнутое уведомление `«3 новых сообщения · Фудзияма Арбат»` через `tag`/`collapse-key` = id чата, а не N отдельных.
- **Не слать автору собственные** сообщения; учитывать «прочитано» (если тред открыт — не пушить).
- **Badge** на иконке PWA — число непрочитанных чатов (`app_badge` в declarative / Badging API).
- Тон/приоритет — как у мессенджера: немедленно, с превью, без задержки батчинга (в отличие от новостей).

### Остальные события

| Событие | Тип (тумблер) | Payload / поведение |
|---|---|---|
| Новое сообщение в чате (заявка/объект) | `chat` 🔵 | см. §6.0 — главный |
| Новая заявка (на объекте/в зоне) | `ticketNew` | «Новая заявка #N · объект · категория» → карточка |
| Назначение на меня | `assignment` | «Вам назначена заявка #N» → карточка |
| Комментарий по заявке | `chat`/`comment` | по сути чат-сообщение (см. CHAT-purpose) |
| Добавлено фото/видео | `chat` | «Добавлено фото · #N» → вкладка Чат/Фото |
| Смена статуса заявки | `statusChange` | «Заявка #N → В работе» |
| Готово к приёмке | `acceptance` | «#N готова к приёмке» (клиенту-приёмщику) |
| Отклонение приёмки → доработка | `acceptanceReject` | «#N вернули на доработку» (технику) — критично |
| SLA-предупреждение / просрочка | `sla` | «⏰ #N: до просрочки 1ч» / «просрочена» |
| Новости/рассылки | `news` | по умолчанию OFF; батчатся |

## 7. Настройки (пользовательские тумблеры)

Экран в Профиле → «Уведомления»: мастер-тумблер + по типам (маппинг на `PushPreference`):
- **Сообщения в чатах** (по умолчанию ON) — главный
- Новые заявки (ON)
- Назначения (ON)
- Приёмка / отклонение (ON)
- SLA (ON)
- Смена статуса (ON)
- Новости (OFF)
- опц. «Не беспокоить» (тихие часы `quietHoursFrom/To`)

Диспетчер на бэке **перед постановкой в очередь** проверяет соответствующий флаг → не шлём выключенные типы. Отдельно — состояние системного разрешения браузера (granted/denied/default) отображается в этом же экране (см. §8).

## 8. UX (разрешение и статусы)

- **Первый запуск:** НЕ просить разрешение сразу. Сначала — **мягкий pre-prompt** (объясняем ценность: «Получайте сообщения из чатов и назначения, даже когда приложение закрыто»), затем по кнопке — системный `requestPermission()`.
- **iPhone-онбординг установки:** если открыто во вкладке Safari (не standalone) — показать гайд «Добавьте на экран „Домой", чтобы включить уведомления» (иначе push технически невозможен). Определять standalone: `navigator.standalone` / `display-mode: standalone`.
- **Повторный запрос:** если `denied` — системно повторно спросить нельзя; показываем инструкцию «включите в Настройках iOS/браузера» + диплинк, где возможно.
- **Отключение:** мастер-тумблер OFF → `DELETE /push/subscriptions` (или мягко на бэке); logout снимает подписку устройства.
- **Статус в настройках:** явно показывать: разрешение (granted/denied), подписка активна (да/нет), устройство (platform), кнопка «Отправить тест».

## 9. Apple / iPhone — детально (ограничения)

Каждое ограничение и его следствие:

1. **Только home-screen PWA.** Push невозможен во вкладке Safari. → Нужен онбординг установки; часть пользователей не установят — для них push недоступен (fallback: realtime при открытом app + бейдж).
2. **iOS 16.4+ обязателен.** Старее — push нет вообще.
3. **Разрешение только по жесту.** Нельзя авто-промпт. → UX §8.
4. **Нет авто-промпта установки.** В отличие от Android (`beforeinstallprompt`), iOS требует ручного Add to Home Screen. → свой гайд.
5. **Подписки «пропадают».** Известный неустранённый баг: подписка может исчезнуть без причины. → обязателен `pushsubscriptionchange` + периодическая проверка/переподписка при заходе.
6. **Очистка хранилища.** iOS может очистить script-writable storage при неиспользовании ~недели → подписка мертва. → TTL-чистка на бэке + переподписка на фронте.
7. **Ниже надёжность доставки**, чем у нативных APNs-приложений. → не полагаться на push как на единственный канал критичных вещей; дублировать состоянием при открытии app.
8. **Нет rich-media как в нативе** (ограниченные картинки/actions в старых версиях; Declarative расширяет `app_badge`, `navigate`). 
9. **Badging** — через `app_badge` (declarative) / Badging API (в standalone).
10. **iOS 26+**: сайты с домашнего экрана по умолчанию открываются как web-app — упрощает попадание в «правильный» режим.

**Можно ли нативно-подобно без App Store?** Частично: **push при закрытом app — да** (для установленной PWA), но с оговорками надёжности выше. Полный паритет с нативом (гарантированная доставка, background-обработка, VoIP-пуши, критические уведомления) — **нет**, это привилегии App Store-приложений. Максимально близкое решение = установленная PWA + гибрид SW/Declarative + аккуратный lifecycle подписок.

## 10. Android — дополнительно

- **Работает из коробки** в браузере (без установки), в фоне/закрытым — полноценно.
- `beforeinstallprompt` — можно предложить установку PWA программно (лучше UX, но для push не обязательно).
- Богатые уведомления: картинки, `actions` (кнопки «Ответить»/«Открыть»), группировка, каналы.
- Транспорт — FCM, но через стандартный Web Push (свой FCM-проект/SDK не нужен).
- Делает Android «эталонной» платформой для чат-push — начинать откатку и демо стоит с него.

## 11. Масштабирование (десятки тысяч push/день и выше)

- **Очередь + пул stateless-воркеров** (Kafka/Redis/pg-boss). Диспетчер только ставит задачи; воркеры доставляют. Горизонтальное масштабирование числом воркеров.
- **Fan-out на устройства** на этапе диспетчера (один юзер = N подписок).
- **Батчинг для некритичных** (новости) — схлопывать; **чат/SLA — немедленно**, без батч-задержки.
- **Rate limits платформ:** учитывать лимиты push-сервисов (напр. FCM HTTP v1 — сотни тысяч сообщений/мин на проект; APNs — персистентные HTTP/2-соединения). Десятки тысяч/день — **сильно ниже** лимитов, узкое место будет не в квотах, а в lifecycle-менеджменте подписок.
- **Главная сложность масштаба — не код доставки, а управление жизненным циклом токенов/подписок** (чистка 410, дедуп, невалидные съедают квоту на no-op). Заложить это сразу.
- **Мониторинг:** доставлено/провалено/протухло (PushDeliveryLog + метрики), алерты на всплеск ошибок.
- **Опция build-vs-buy:** зрелые провайдеры (OneSignal / Knock / собственный на `web-push`+`pg-boss`). Для контроля данных и РФ-специфики — вероятно свой сервис на `web-push`; провайдер — если нужно быстро.

## 12. Безопасность

- **VAPID** (public/private) — идентифицирует наш сервер push-сервису; приватный ключ только в secret-manager/env.
- **HTTPS обязателен** — SW и Web Push работают только на secure origin (у нас уже HTTPS).
- **Шифрование payload** (RFC 8291) — библиотека `web-push` шифрует тело под ключи подписки (`p256dh`/`auth`); push-сервис не читает содержимое.
- **Приватность превью:** тело чат-push содержит текст сообщения — на заблокированном экране виден превью. Дать пользователю опцию «скрывать превью» (слать «Новое сообщение» без текста).
- **Авторизация подписок:** привязка `PushSubscription.userId`; при logout — удалять; не слать чужие данные на устройство после смены пользователя.
- **Минимум PII в payload:** только необходимое; чувствительное подтягивать при открытии по `navigate`.

## Итоговые разделы

### Ограничения (сводка)
- iPhone: только установленная PWA, iOS 16.4+, жест для разрешения, «пропадающие» подписки, ниже надёжность, нет паритета с App Store.
- Все iOS-браузеры = WebKit (одинаковые ограничения).
- Разрешение `denied` необратимо программно (только руками в настройках).

### Риски
- **iOS-надёжность:** часть чат-push может не дойти → дублировать бейджем/состоянием при открытии; не единственный канал для критичного.
- **Низкая установка PWA на iPhone** (ручной Add to Home Screen) → без неё push недоступен; нужен сильный онбординг.
- **Потеря подписок** → без lifecycle-логики база подписок деградирует.
- **Приватность превью чата** на локскрине → опция скрытия.
- **Backend-объём:** новая инфра (очередь/воркеры/VAPID) — не тривиальна, shared zone.

### Схема данных → §4.1 · API → §4.2 · UX → §8 · Безопасность → §12 · Масштабирование → §11

### Рекомендации (порядок)
1. **MVP на Android/Chrome первым** — там паритет с нативом, быстрый результат, отладка бэкенда/воркеров/VAPID без iOS-специфики.
2. **Чат-push — первая фича** (не «новые заявки»), т.к. чат = основная рабочая зона. Один тип события, максимальная ценность.
3. **iOS вторым** — добавить онбординг установки PWA + `pushsubscriptionchange` lifecycle + Declarative fallback (iOS 18.4+).
4. **Гибрид SW + Declarative Web Push** — богатые группированные чат-уведомления через SW, декларативный fallback для надёжности на новых iOS.
5. **Lifecycle подписок с первого дня** — чистка 410, TTL по lastSeenAt, переподписка. Это определяет, будет ли решение работать на масштабе.
6. **Настройки-тумблеры + pre-prompt UX** — чтобы не выжечь разрешения (denied необратим).
7. **Backend — согласовать с management** как отдельный раунд (сущности + очередь + воркеры + VAPID). Связано с направлением «Чат до уровня Telegram» и P0.1/P1.6/P1.7 из `MOBILE_BACKEND_REQUIREMENTS_V1.md`.
