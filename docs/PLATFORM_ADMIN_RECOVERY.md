# Восстановление доступа PLATFORM_ADMIN — Stage и Production

Документ описывает единственный разрешённый способ создать первого
`PLATFORM_ADMIN` при новом развёртывании и восстановить доступ, если
действующего администратора платформы не осталось.

---

## Что изменилось и почему (SMA-SECURITY-P1)

Раньше привилегированный аккаунт мог появиться сам. `AuthService.login()`
вызывал `ensurePlatformAdmin()` **до проверки пароля**, поэтому при
настроенных `PLATFORM_ADMIN_EMAIL` и `PLATFORM_ADMIN_PASSWORD`:

- любой неаутентифицированный `POST /auth/login` — с любыми, даже
  заведомо неверными учётными данными — создавал пользователя с ролью
  `PLATFORM_ADMIN` и при необходимости платформенную организацию;
- удаление такого аккаунта не держалось: следующий же запрос к `/auth/login`
  воссоздавал его с паролем из окружения;
- при настроенной только одной из двух переменных вход возвращал
  `400` **всем** пользователям, то есть сломанное окружение превращалось в
  отказ обслуживания, видимый снаружи.

Этот путь удалён полностью: ни вызова, ни самого метода в коде больше нет.
Вход никого не создаёт и никому не повышает прав.

Создание выполняется только отдельной операцией, описанной ниже.

---

## Процедура: первый запуск нового развёртывания

Выполняет оператор с доступом к контейнеру бэкенда. Доступ к контейнеру и
есть граница авторизации: через HTTP этой операции не существует, нового
endpoint не добавлялось.

### 1. Подготовить пароль вне истории команд

Пароль не должен попасть ни в историю shell, ни в `docker-compose`, ни в
журналы. Читаем его с приглашения, не отображая:

```bash
read -rsp 'PLATFORM_ADMIN_PASSWORD: ' PA_PASS && echo
```

### 2. Запустить операцию

В production-образе devDependencies отсутствуют, поэтому `ts-node` не нужен:
скрипт собирается вместе с бэкендом и запускается обычным `node`.

```bash
docker exec -i -e PLATFORM_ADMIN_BOOTSTRAP_CONFIRM=create-platform-admin \
  -e PLATFORM_ADMIN_EMAIL='admin@example.com' \
  -e PLATFORM_ADMIN_PASSWORD="$PA_PASS" \
  <backend-container> node dist/scripts/create-platform-admin.js

unset PA_PASS
```

В окружении разработки доступен и вариант через ts-node:
`npm run platform:admin:create`.

### 3. Проверить вывод

Успешное создание:

```
[create-platform-admin] target database: <имя базы>
[create-platform-admin] created company: СМА-Тех
[create-platform-admin] created user: admin@example.com (PLATFORM_ADMIN)
```

Строка `target database` печатается специально: ошибиться контуром легко, а
имя базы секретом не является. Если база не та — ничего не делать и
разобраться с адресацией.

### 4. Сменить пароль после первого входа

Пароль, заданный при bootstrap, считается одноразовым: он проходил через
окружение. После первого входа сменить его штатными средствами.

---

## Переменные окружения

| Переменная | Обязательна | Назначение |
|---|---|---|
| `PLATFORM_ADMIN_BOOTSTRAP_CONFIRM` | да | Подтверждение оператора. Ровно `create-platform-admin` |
| `PLATFORM_ADMIN_EMAIL` | да | Email создаваемого администратора |
| `PLATFORM_ADMIN_PASSWORD` | да | Пароль. Только на время запуска |
| `PLATFORM_ADMIN_FIRST_NAME` | нет | По умолчанию `Platform` |
| `PLATFORM_ADMIN_LAST_NAME` | нет | По умолчанию `Admin` |
| `PLATFORM_COMPANY_NAME` | нет | По умолчанию `СМА-Тех` |
| `PLATFORM_COMPANY_TIMEZONE` | нет | По умолчанию `UTC` |

**Важно:** держать `PLATFORM_ADMIN_EMAIL` и `PLATFORM_ADMIN_PASSWORD`
постоянно прописанными в окружении контейнера больше не нужно и не следует.
Сами по себе они ничего не создают, но постоянно хранить пароль
привилегированного аккаунта в конфигурации незачем.

---

## Что операция делает и чего не делает

Делает:

- создаёт пользователя с ролью `PLATFORM_ADMIN`, если такого email нет;
- создаёт платформенную организацию, если её ещё нет;
- печатает имя целевой базы для проверки оператором.

Не делает **никогда**:

- не меняет пароль действующего аккаунта;
- не повышает роль существующему пользователю — если email занят другой
  ролью, операция отказывает, а не переписывает роль;
- не удаляет и не деактивирует ничего;
- не печатает пароль; при ошибке печатает только класс и код ошибки, потому
  что полный объект ошибки Prisma содержит аргументы запроса, а среди них
  хеш пароля.

Повторный запуск безопасен: если действующий `PLATFORM_ADMIN` с таким email
уже есть, операция сообщает `no changes` и ничего не меняет. Дубликатов не
возникает.

## Восстановление, когда администратор платформы потерян

1. Убедиться, что администратора действительно нет:

```bash
docker exec -i <backend-container> node -e "
const {PrismaClient}=require('@prisma/client');const p=new PrismaClient();
p.user.findMany({where:{role:'PLATFORM_ADMIN'},select:{email:true,isActive:true}})
 .then(r=>{console.log(r);return p.\$disconnect()})"
```

2. Если аккаунт существует, но деактивирован — вопрос решается не bootstrap,
   а активацией пользователя: операция намеренно не трогает существующие
   записи.

3. Если аккаунтов нет — выполнить процедуру из раздела «Первый запуск» с
   новым email либо с прежним.

4. Если email занят обычным пользователем — операция откажет. Это
   осознанное поведение: автоматическое повышение существующего аккаунта до
   `PLATFORM_ADMIN` было бы путём эскалации привилегий. Выбрать другой email
   или разобраться с владельцем аккаунта вручную.

---

## Границы, которые нельзя ослаблять

- Через HTTP создания привилегированного пользователя не существует. Если
  когда-нибудь потребуется, это не должно быть незащищённым endpoint.
- Подтверждение `PLATFORM_ADMIN_BOOTSTRAP_CONFIRM` проверяется **первым**,
  раньше всех остальных условий: настроенного окружения недостаточно, нужно
  отдельное осознанное действие оператора.
- Решение о создании вынесено в чистый модуль
  `backend/src/auth/platform-admin-bootstrap.ts` и закреплено тестами
  `platform-admin-bootstrap.spec.ts` и `auth.login-bootstrap.spec.ts`.
  Правила проверяются исполнением: при возвращении bootstrap в `login()`
  тесты падают.
