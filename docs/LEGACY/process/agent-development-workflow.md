# Agent Development Workflow

> Source of Truth для того, **как** агенты вносят изменения в этот репозиторий.
> Связанные документы: [Module Boundaries](./module-boundaries.md) ·
> [Deployment Workflow](../../process/deployment-workflow.md).

## Purpose

Зафиксировать единые правила работы агентов: как декомпозируется работа, что
проверяется перед коммитом и пушем, как оформляются Pull Request'ы и как
изменения попадают на Stage и в Production.

Документ обязателен к соблюдению для **всех** агентов (AI Developer, AI QA,
AI DevOps и т.д.) и для людей, выполняющих ту же роль.

## Ownership Model

Каждое изменение принадлежит ровно одной задаче и одной зоне ответственности.
Границы модулей описаны в [Module Boundaries](./module-boundaries.md).

- Агент работает только внутри своей зоны ответственности.
- Изменения вне зоны требуют **отдельной задачи** и отдельного approval.
- Backend остаётся источником истины для прав доступа; UI-гейтинг не заменяет
  серверные проверки.

## One Task = One Commit

**Одна задача — один коммит.** Коммит должен содержать изменения ровно одной
задачи, без «попутных» правок.

- Не смешивать в одном коммите разные задачи.
- Не подбирать в staging чужие/несвязанные изменения рабочего дерева.
- Сообщение коммита описывает одну задачу (`type(scope): summary`).

## Commit Gate

Перед каждым коммитом обязательно выполнить и пройти **все** проверки:

1. **Build** — проект собирается без ошибок (`npm run build` для `web/`,
   соответствующая сборка для других модулей).
2. **Scope Check** — изменения не выходят за зону ответственности задачи
   (см. [Module Boundaries](./module-boundaries.md)).
3. **Changed Files Review** — просмотреть полный список изменённых файлов:

   ```bash
   git status
   git diff
   ```

4. **Staged Files Review** — застейджить только относящиеся к задаче файлы и
   проверить, что в индексе нет лишнего:

   ```bash
   git add -- <only task files>
   git diff --cached --name-status
   git diff --cached
   ```

Если хотя бы одна проверка не пройдена — коммит не делается.

## Push Gate

Перед каждым push обязательно проверить, что уходит **только** работа по текущей
задаче и нет посторонних коммитов:

```bash
git log origin/<branch>..HEAD --oneline
```

- В выводе должны быть только коммиты текущей задачи.
- При наличии unrelated commits push не выполняется — состояние ветки
  приводится в порядок (rebase/reset/новая ветка) и проверка повторяется.
- Push выполняется только после явного approval.

## Pull Request Rules

- Один PR соответствует одной задаче (следствие *One Task = One Commit*).
- Описание PR содержит: задачу/ID, что изменено, как проверено (build,
  scope, smoke).
- PR не затрагивает файлы вне зоны ответственности задачи.
- Merge — только после ревью и зелёных проверок. PR не мержит сам себя.

## Stage Deployment Rules

Деплой на Stage выполняется по [Deployment Workflow](../../process/deployment-workflow.md)
и только после approval.

- Обязательны: Backup → Pull → Build → Smoke Test.
- Никаких локальных hotfix'ов прямо на сервере — изменения идут только через
  коммит в репозитории.

## Production Deployment Rules

Production — наиболее охраняемый контур. Подробности и чеклист — в
[Deployment Workflow](../../process/deployment-workflow.md).

- **Stage Validation Required** — изменение должно быть проверено на Stage.
- **Backup Required** — перед деплоем обязателен бэкап.
- **Smoke Test Required** — после деплоя обязателен smoke test.
- Деплой в Production — только после явного approval. Агент никогда не
  деплоит в Production автономно.
