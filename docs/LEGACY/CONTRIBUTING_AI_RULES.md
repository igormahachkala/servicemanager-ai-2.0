# CONTRIBUTING_AI_RULES — ServiceManager.AI

Этот документ описывает правила работы с AI (ChatGPT и другими LLM),
чтобы развитие проекта было безопасным, последовательным и масштабируемым.

---

# 1. ОБЩИЕ ПРАВИЛА

AI должен:

- Работать строго в рамках текущего проекта ServiceManager.AI
- Учитывать мульти-тенант архитектуру (companyId везде)
- Не предлагать случайные Linux-команды без запроса
- Не менять структуру проекта без объяснения последствий
- Не ломать существующие модули

AI не должен:

- Хардкодить токены
- Хардкодить JWT
- Вставлять production-пароли
- Предлагать хранить секреты в коде
- Предлагать обходить guards/roles/security

---

# 2. БЕЗОПАСНОСТЬ

Всегда соблюдать:

- JWT всегда динамический (через /auth/login)
- Секреты только в .env
- Никаких токенов в коде
- Никаких токенов в репозитории
- Никаких паролей в документации

Если требуется тестовый токен — использовать пример, не реальный.

---

# 3. АРХИТЕКТУРНЫЕ ПРИНЦИПЫ

Проект построен на:

- NestJS modular architecture
- Prisma ORM
- PostgreSQL
- Multi-tenant via companyId
- JWT-based authentication
- Role-based access (RolesGuard)

AI должен:

- Помещать бизнес-логику только в service
- Не переносить логику в controller
- Не писать raw SQL без крайней необходимости
- Сохранять разделение модулей

---

# 4. ДОБАВЛЕНИЕ НОВОГО МОДУЛЯ

Перед созданием нового модуля AI должен:

1. Объяснить зачем он нужен
2. Показать как он впишется в текущую архитектуру
3. Показать Prisma изменения (если есть)
4. Указать миграцию
5. Указать подключение в AppModule

---

# 5. ИЗМЕНЕНИЯ В БД

Перед изменением schema.prisma AI обязан:

- Объяснить влияние на существующие данные
- Проверить связи
- Указать возможные конфликты
- Предложить имя миграции

Нельзя:

- Удалять поля без обсуждения
- Ломать связи
- Удалять ограничения уникальности без объяснения

---

# 6. AUTO ASSIGN & BUSINESS LOGIC

AI не должен:

- Упрощать алгоритмы без обсуждения
- Убирать multi-tenant фильтрацию
- Назначать техника без проверки companyId

---

# 7. РАБОТА С GIT

AI не должен:

- Предлагать force push без объяснения
- Предлагать удаление веток без причины
- Предлагать удаление истории

---

# 8. МАСШТАБИРОВАНИЕ

При предложении новых фич AI должен учитывать:

- Возможность масштабирования
- Будущий billing
- Будущую аналитику
- Мобильный клиент
- SLA

---

# 9. ФОРМАТ ОТВЕТА AI

Если изменение касается кода, AI должен:

1. Кратко объяснить что делаем
2. Дать точные команды
3. Дать код полностью (не кусками)
4. Указать куда вставлять
5. Указать что перезапустить

---

# 10. КОНТЕКСТ

Перед работой AI должен учитывать:

- docs/00_START_HERE.md
- docs/02_ARCHITECTURE.md
- docs/API_SPEC.md
- docs/SECURITY_MODEL.md

Если контекст не предоставлен — AI должен попросить его.

---

# 11. ГЛАВНЫЙ ПРИНЦИП

Проект ServiceManager.AI — это production-ready SaaS,
а не учебный pet-проект.

Любые изменения должны быть совместимы
с будущим масштабированием и коммерциализацией.

# 12. НОВОЕ ПРАВИЛО РАБОТЫ С ФАЙЛАМИ (СТРОГИЙ РЕЖИМ)

Работа с файлами ведётся только по следующему протоколу:

## 12.1 Поиск файла

Пользователь даёт команду найти нужный файл (или просит AI назвать точный путь).
Допустимые команды поиска:

- `find ~/projects/sma-service -name "имя_файла"`
- `ls` / `ls -la` по конкретной директории

## 12.2 Полный вывод файла

Пользователь копирует **весь файл полностью** в чат (без сокращений).
Если файл большой — несколькими частями через `sed -n '1,260p' ...`, затем `sed -n '260,520p' ...` и т.д.

## 12.3 Полная готовая версия файла

AI возвращает **полную готовую версию файла целиком**.

❗ Запрещено:
- “вставь кусочек”
- “замени пару строк”
- “добавь вот сюда”
- любые частичные патчи и фрагменты

Только полный файл.

## 12.4 Команды на замену / сохранение / пересборку

После выдачи полного файла AI обязан дать пользователю инструкции:

- как открыть файл
- как полностью заменить содержимое
- как сохранить
- как перезапустить/пересобрать (docker compose / npm / prisma)

Пример формата:

1) Открыть файл:
- `nano путь/к/файлу`

2) Вставить полный файл (заменить всё содержимое)

3) Сохранить:
- `Ctrl + O` → `Enter` → `Ctrl + X`

4) Пересобрать/перезапустить:
- `docker compose restart backend`
или
- `docker compose up -d --build --force-recreate`
или
- `npm run build` / `npm run start:dev`

## 12.5 Почему это правило обязательно

Частичные вставки часто приводят к:
- пропущенным запятым (package.json)
- дублированию кода
- битым импортам
- несоответствию скобок/типов
- скрытым ошибкам форматирования

Полная замена файла снижает количество глупых ошибок примерно на 90%.
