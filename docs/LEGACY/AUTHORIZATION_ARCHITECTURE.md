# AUTHORIZATION ARCHITECTURE — ServiceManager.AI

Этот документ описывает архитектуру авторизации
в системе ServiceManager.AI.

Система использует трехуровневую модель доступа:

1) Authentication
2) Permission (PBAC)
3) Data Policy


--------------------------------------------------

1. Authentication

Authentication отвечает на вопрос:

КТО пользователь.


Используется:

JWT


JWT содержит:

- userId
- companyId
- role


JWT проверяется через:

JwtGuard


Без JWT пользователь не может
выполнять защищенные операции.


--------------------------------------------------

2. Permission Layer (PBAC)

Permission отвечает на вопрос:

МОЖЕТ ЛИ пользователь выполнить действие.


Используется:

PermissionGuard


PermissionGuard проверяет:

PermissionBlock → RolePermission


Пример:

@Permissions(PERMISSIONS.TICKETS_ASSIGN)


Это означает:

роль пользователя должна иметь
permission TICKETS_ASSIGN.


--------------------------------------------------

3. Role-based fallback

В системе сохраняется
ограниченная поддержка ролей.

Используется:

RolesGuard


Но роль не должна быть
основной моделью доступа.

Основная модель:

PBAC.


--------------------------------------------------

4. Policy Layer

Policy отвечает на вопрос:

К КАКИМ ДАННЫМ применимо действие.


Пример:

TECHNICIAN может:

- видеть только свои тикеты
- claim NEW тикеты
- менять статус своих тикетов


Это реализуется через:

Policy functions.


--------------------------------------------------

5. Policy файлы

Policy находятся в:

backend/src/policy


Текущие политики:

tickets.policy.ts  
users.policy.ts


Policy возвращают:

scope conditions.


--------------------------------------------------

6. Пример полной цепочки

Endpoint:

PATCH /tickets/:id/status


Шаг 1

JwtGuard

проверяет JWT.


Шаг 2

PermissionGuard

проверяет permission:

TICKETS_STATUS_CHANGE.


Шаг 3

Policy

проверяет:

можно ли менять
конкретный тикет.


--------------------------------------------------

7. Разделение ответственности

Guard

отвечает за:

МОЖНО ЛИ ДЕЙСТВИЕ


Policy

отвечает за:

К КАКИМ ДАННЫМ
применимо действие


Service

выполняет
бизнес операцию.


--------------------------------------------------

8. Архитектурное правило

Guard никогда не должен
знать бизнес-логику.

Policy никогда не должен
изменять данные.

Service никогда не должен
обходить Policy.


--------------------------------------------------

9. Multi-tenant безопасность

Любая Policy должна учитывать:

companyId.


Это предотвращает:

cross-company доступ.


--------------------------------------------------

10. Архитектурная цель

ServiceManager.AI должен использовать
enterprise модель авторизации:

Authentication  
→ Permission  
→ Policy


Это соответствует архитектуре
enterprise SaaS систем.
