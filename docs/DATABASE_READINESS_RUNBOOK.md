# Runbook: готовность базы данных и оперативные проверки

Дежурные проверки для контуров Stage и Production. Относится к issue #378.

---

## Два разных маршрута

| Маршрут | Что отвечает | К базе обращается | Назначение |
|---|---|---|---|
| `GET /health` | `{"status":"ok"}`, всегда 200 | **нет** | liveness: процесс жив, перезапускать нечего |
| `GET /health/ready` | 200 при готовности, **503** при недоступной базе | да, один `SELECT 1` | readiness: можно ли обслуживать запросы |

Почему разделены: `/health` не обращался и не обращается к базе, поэтому
отвечал `ok` даже при лежащей PostgreSQL. При этом именно `/health`
используется как проверка приёмки в канонических скиллах выкладки
(`sma-deploy-prod`, `sma-deploy-stage` ожидают 200) — то есть выкладка
проходила и при недоступной базе. Контракт `/health` намеренно не менялся:
он нужен как дешёвый liveness. Готовность вынесена на отдельный маршрут.

---

## Проверка вручную

```bash
# liveness — всегда 200, пока процесс жив
curl -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3001/health

# readiness — 200 или 503
curl -s -w '\nHTTP %{http_code}\n' http://127.0.0.1:3001/health/ready
```

Ответ при готовности:

```json
{"status":"ready","database":"up","latencyMs":3}
```

Ответы при неготовности (код **503**):

```json
{"status":"not_ready","database":"down"}
{"status":"not_ready","database":"timeout","timeoutMs":2000}
```

`database` различает сеть и отказ: `timeout` означает, что база не ответила в
отведённое время, `down` — что соединение не состоялось или запрос отклонён.
Для probe-клиента оба случая одинаковы — 503.

## Что означает каждый результат

| Наблюдение | Трактовка | Действие |
|---|---|---|
| `/health` 200, `/health/ready` 200 | норма | — |
| `/health` 200, `/health/ready` 503 `down` | процесс жив, база недоступна | проверить контейнер базы, сеть, пул соединений. Перезапуск бэкенда не поможет |
| `/health` 200, `/health/ready` 503 `timeout` | база отвечает слишком медленно | проверить нагрузку, блокировки, место на диске |
| `/health` не отвечает | процесс не жив | смотреть логи бэкенда, перезапуск уместен |
| `/health/ready` 200, но пользователи видят ошибки | проблема не в связности базы | смотреть логи приложения, миграции, права |

Деталей ошибки в ответе нет намеренно: маршрут публичный, как и `/health`, а
сообщения драйвера содержат хост, имя базы и иногда пользователя. Причину
смотреть в логах бэкенда, а не в теле ответа.

## Настройка

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DB_READINESS_TIMEOUT_MS` | `2000` | Предел ожидания проверки. Зажимается в диапазон 100…10000; мусор и ноль дают значение по умолчанию |

Результат кэшируется на 1 секунду: это ограничивает нагрузку на базу одним
запросом в секунду при любой частоте опроса, включая обращения извне.

## Сопутствующие проверки

Готовность приложения — не то же самое, что исправность базы. Отдельно:

```bash
# статус миграций
docker exec <backend> npx prisma migrate status

# занятое место под данными
docker exec <postgres> df -h /var/lib/postgresql/data

# активные соединения
docker exec <postgres> psql -U <user> -d <db> -c \
  "SELECT count(*), state FROM pg_stat_activity GROUP BY state;"
```

Команды выше — только чтение.

---

## Чего этот маршрут НЕ доказывает

`/health/ready` подтверждает связность с базой — и ничего более. Он **не**
является свидетельством:

- наличия и свежести резервных копий;
- успешности восстановления;
- выполнения RPO/RTO;
- сохранности `uploads`.

Требования к этому — в `docs/DATABASE_BACKUP_REQUIREMENTS.md`. Отмечать их
выполненными можно только по фактическим прогонам, а не по наличию кода.
